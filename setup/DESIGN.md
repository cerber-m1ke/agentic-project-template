## 1. Назначение и границы

**Agentic Project** — рабочая среда, в которой Агент комфортно работает над всеми Ресурсами проекта.
Проект — это не один репозиторий, а связанное множество: репозитории-ресурсы, Знания о них, инструменты
и инструкции. Набор ресурсов у разных людей в команде может отличаться — это нормально.

**agentic-project-template** — шаблон, из которого такие проекты разворачиваются и через который обновляются.

**Цели:**

- быстро развернуть новый проект или «обернуть» существующие репозитории;
- не зависеть от конкретного Агента: Claude Code и Codex на старте, безболезненное добавление других,
  включая опенсорсные и китайские;
- не зависеть от хостовой системы: macOS, Linux и Windows с первого дня;
- копить Знания внутри проекта под git, а не в системных каталогах агентов (`~/.claude` и т.п.);
- экономить контекст: старт сессии дешёвый, Знания подтягиваются по требованию;
- обновлять проект из свежей версии шаблона силами Агента, под контролем человека;
- поставляться на двух языках: русском (по умолчанию) и английском.

**Не цели v1:**

- регламентировать содержимое Ресурсов;
- политика провайдеров и конфиденциальности данных (отложено);
- специальные механизмы командной синхронизации Знаний (корневой репозиторий можно расшарить как есть);
- семантический (векторный) поиск.

## 2. Термины

| Термин | Значение |
|---|---|
| Шаблон | Репозиторий `agentic-project-template` |
| Проект | Папка, развёрнутая из шаблона; корневой git-репозиторий |
| Ресурсы | То, над чем работаем (`Resources/`), чаще всего — отдельные git-репозитории |
| Знания | Постоянная память проекта (`Knowledge/`) |
| Модуль | Единица payload: набор файлов в раскладке проекта + шаги установки |
| Профиль | Именованный набор модулей под тип проекта |
| Язык проекта | `ru` или `en`; выбирается при init, определяет язык всех переводимых файлов |
| Релиз | Версия шаблона, отмеченная git-тегом `vX.Y.Z` |
| Адаптер | Всё, что нужно конкретному Агенту, чтобы увидеть систему проекта |
| Управляемый файл | Файл, которым владеет шаблон; обновляется при update |
| Библиотекарь | Процедура поиска и проверки ответов в Знаниях (skill + субагент) |

## 3. Принципы

1. **`.agents/` — единственный источник правды** для всего системного. Каталоги конкретных агентов
   (`.claude/`, `.codex/`, …) генерируются и в git не попадают.
2. **Плавная деградация.** Всё работает у агента, который умеет только читать `AGENTS.md` и выполнять
   команды. Нативные skills, субагенты и хуки — улучшение, а не требование.
3. **В Знаниях — только то, что не выводится** из Ресурсов и истории git.
4. **Механику делает скрипт, смысл — Агент.** Детерминированные идемпотентные операции (структура, ссылки,
   конфиги, миграции) — в Toolbox. Интервью, анализ, тексты — в skills.
5. **Дешёвый старт.** При старте в контекст попадают только `AGENTS.md` и описания skills.
6. **Никаких пустых каталогов.** В каждом каталоге лежит README с правилами или шаблоны — это заодно
   инструкция Агенту.
7. **Необратимое подтверждает человек:** инициализацию, обновление, коммиты (по команде или явной просьбе).

## 4. Структура развёрнутого проекта

```
<project>/
├── AGENTS.md                 # точка входа для всех агентов
├── README.md                 # о проекте — для человека
├── .gitignore  .gitattributes  .ignore
├── .agents/                  # системное, источник правды
│   ├── agentic.lock          # происхождение из шаблона, профиль, модули, хэши управляемых файлов
│   ├── local.toml            # настройки этой машины (подключённые агенты), не в git
│   ├── skills/               # процедуры (стандарт Agent Skills)
│   ├── agents/               # субагенты в каноническом формате
│   ├── hooks/                # hooks.toml с абстрактными событиями + скрипты
│   ├── git-hooks/            # хуки git (pre-commit: kb lint, поиск секретов)
│   ├── adapters/<agent>/     # манифесты адаптеров
│   ├── mcp.toml              # каноническое описание MCP-серверов
│   ├── permissions.toml      # правила разрешений (deny/ask/allow) для всех агентов
│   └── docs/                 # концепция и справка — читаются по требованию
├── Knowledge/                # хранилище Obsidian
│   ├── README.md             # общие правила Знаний
│   ├── _templates/           # шаблоны заметок (tb kb new + Obsidian)
│   └── Decisions/ Entities/ Examples/ Gotchas/ Plans/ Tasks/   # в каждом — README.md с правилами
├── Resources/
│   ├── README.md             # правила работы с ресурсами
│   ├── resources.toml        # каталог ресурсов проекта
│   └── <name>/               # склонированные ресурсы (не в корневом git)
├── Toolbox/
│   ├── README.md             # индекс инструментов
│   ├── tb  tb.cmd            # единая точка входа
│   ├── agentic/              # инструменты шаблона (управляемые)
│   └── …                     # инструменты проекта
├── Runtime/                  # не в git
└── .claude/  .codex/  CLAUDE.md  …   # генерируемые адаптеры, не в git
```

Состав зависит от профиля и модулей ([§5.3](#53-модули-и-профили)). Имена корневых каталогов фиксированы,
регистр важен.

В `Runtime/` за системой зарезервированы `tools/`, `cache/` и `update/`. Остальная структура — на усмотрение
исполнителя.

## 5. Репозиторий шаблона

### 5.1. Раскладка: setup и payload

```
agentic-project-template/
├── AGENTS.md          # для агента: разработка шаблона или инициализация (→ setup/INIT.md)
├── README.md          # концепция — для человека (русский)
├── README.en.md       # то же на английском
├── CHANGELOG.md       # версии и миграции
├── init.sh  init.cmd  # вход в инициализацию
├── setup/             # инсталлятор, в проект не попадает
│   ├── DESIGN.md      # этот документ
│   ├── INIT.md        # инструкция агенту по инициализации
│   ├── UPDATE.md      # инструкция агенту по обновлению (исполняется из свежей копии шаблона)
│   ├── VERSION
│   ├── init.py  update.py
│   ├── i18n_check.py  # проверка парности переводов
│   ├── profiles/      # профили: какие модули и с какими параметрами
│   └── migrations/    # детерминированные миграции между версиями
└── payload/
    └── modules/<module>/…   # файлы модулей в раскладке проекта; переводимые — парами *.ru.* / *.en.*
```

Шаблон сам не является Agentic Project: генератор и результат не смешиваются. Собственные решения шаблона
живут в этом документе и в `CHANGELOG.md`.

Файлы модуля — то, что git отслеживает или готов отследить в `payload/modules/<module>/`: игнорируемое git
(`.idea/`, `.obsidian/`, `Runtime/`) в проект не попадает, а проверка чистоты клона в init его не видит.
Без git (распакованный архив) init обходит каталог модуля и пропускает те же служебные каталоги.

`AGENTS.md` шаблона различает два режима. Если просят развернуть или инициализировать проект, Агент
выполняет `setup/INIT.md`. Иначе он работает над самим шаблоном.

### 5.2. Владение файлами

| Класс | Владелец | Что делает update |
|---|---|---|
| `managed` | шаблон | Перезаписывает, если файл не менялся локально. Иначе — конфликт, решает человек |
| `seeded` | проект (создан из шаблона один раз) | Не трогает; может предложить изменения |
| `project` | проект | Не трогает |

Смешанные файлы (`block`) — `AGENTS.md`, `.gitignore`, `.gitattributes`, `.ignore`: управляемый блок
между маркерами `<!-- agentic:begin -->` и `<!-- agentic:end -->` (в файлах git — `# agentic:begin`
и `# agentic:end`), остальное принадлежит проекту. Маркер — только целая строка: упоминание слов
`agentic:begin` в тексте маркером не считается. Механизмы подключения файлов у агентов разные (`@import`
есть только у Claude), поэтому используем маркеры. Если проект удалил маркеры, update не дописывает блок
заново (старый текст блока остался бы дублем): человек возвращает маркеры, потом обновление повторяется.

Шаблоны заметок `Knowledge/_templates/` — `seeded`: проект подстраивает их под себя (в том числе
в Obsidian), изменения шаблона приходят предложениями.

Класс и хэш каждого установленного файла записываются в `agentic.lock`. Это база для трёхстороннего
сравнения при обновлении: без неё нельзя отличить изменение шаблона от локальной правки. У `seeded`-файла
хэш исходной версии нужен, чтобы предложить изменения шаблона (`seeded-changed`); у `block`-файла
хэшируется только текст между маркерами. Хэш считается после нормализации CRLF → LF.

### 5.3. Модули и профили

Модуль — набор файлов в раскладке проекта плюс необязательные шаги установки. Профиль — список модулей
с параметрами.

| Модуль | Состав |
|---|---|
| `core` | Всегда: `AGENTS.md`, `.agents/`, `Toolbox/agentic/`, правила `Runtime/`, настройки git |
| `knowledge` | `Knowledge/`, `tb kb`, библиотекарь, skills работы со Знаниями |
| `resources` | `Resources/`, каталог, `tb resources` |
| `obsidian` | Настройка хранилища на машине |
| `devcontainer` | Опционально, см. [§10.5](#105-docker-модуль-devcontainer) |

Профили v1: `software` и `generic`. Набор модулей у них одинаковый, различается фрагмент правил
в `AGENTS.md` (`setup/profiles/<profile>.<lang>.md`).

### 5.4. Хостинг и версии

- Шаблон — публичный репозиторий `agentic-project-template` на GitHub.
- URL шаблона записывается в `agentic.lock` при init (берётся из `origin` клона). Проект, развёрнутый
  из форка, обновляется из этого форка.
- Разработка идёт в основной ветке `master`. **Релиз** — это git-тег `vX.Y.Z`. Update берёт последний релиз,
  а не текущее состояние ветки, поэтому незавершённые изменения в проекты не попадают.
- Нумерация по semver:

  | Часть | Когда увеличивается |
  |---|---|
  | major | Нужна миграция структуры проекта или формата Знаний; несовместимо меняются команды `tb` или протокол в `AGENTS.md` |
  | minor | Новые skills, адаптеры, модули, команды `tb` — без поломки существующего |
  | patch | Исправления |

- Начинаем с `v0.1.0`. Пока major равен нулю, формат ещё может меняться, но миграции всё равно обязательны.
- **Между релизами** `setup/VERSION` содержит следующую версию с суффиксом `-dev` (`0.2.0-dev`);
  релизный коммит убирает суффикс и получает тег. Отдельного коммита «начало разработки» после релиза нет:
  `-dev` и раздел «не выпущено» в `CHANGELOG.md` ставит первое изменение после релиза, сразу с нужным шагом
  (patch, minor или major). До него `master` совпадает с тегом, а `setup/VERSION` — с релизом. Раньше
  после каждого релиза шёл коммит на следующий patch, а следующий релиз дважды подряд оказался minor, и
  такие коммиты только засоряли историю. `X.Y.Z-dev` предшествует `X.Y.Z`, поэтому проект,
  развёрнутый из незавершённого состояния, получит релиз обычным обновлением, а init предупреждает
  о таком развёртывании (и о релизной версии без тега на HEAD). Миграция `X.Y.Z` выполняется при переходе
  со старшей версии ниже `X.Y.Z` на `X.Y.Z-dev` и выше — в том числе повторно для проекта из `X.Y.Z-dev`:
  миграции идемпотентны.
- Релиз состоит из раздела в `CHANGELOG.md` (с подразделом «Миграции»), обновлённого `setup/VERSION`
  и тега. Перед релизом обязательно проходит проверка переводов ([§5.5](#55-языки)).

### 5.5. Языки

Шаблон поставляется на русском (по умолчанию) и английском. Язык выбирается при init и записывается
в `agentic.lock`. Проект получает **один** язык: дублирование живёт только в шаблоне и не раздувает
контекст агента.

**Что переводится** — всё, что попадает в проект или первым читает человек:

- `README.md` шаблона (английская версия — `README.en.md`);
- блок шаблона в `AGENTS.md`;
- README каталогов и шаблоны заметок;
- `SKILL.md` и промпты субагентов.

**Что не переводится:**

- `setup/DESIGN.md` — внутренний документ шаблона;
- `AGENTS.md` шаблона, `setup/INIT.md`, `setup/UPDATE.md`, `CHANGELOG.md` — их читает агент и пересказывает
  человеку на языке проекта;
- код, имена файлов и skills, ключи и значения перечислений во frontmatter;
- сообщения `tb` — всегда на английском, их читают в основном агенты.

**Раскладка.** Переводимый файл хранится в payload парой `<name>.ru.<ext>` и `<name>.en.<ext>`. Init
устанавливает нужный вариант под именем `<name>.<ext>`, например `SKILL.en.md` → `SKILL.md`. Хэш
в `agentic.lock` считается от установленного варианта.

**Источник правды — русская версия**, английская производная: агент обновляет её после каждого изменения
русской. `setup/i18n_check.py` проверяет парность: у каждого файла есть пара, совпадают структура
заголовков, блоки кода, команды и ключи frontmatter. Без прохождения проверки релиз не выпускается.

**Смена языка** в развёрнутом проекте — это переустановка `managed`-файлов и блоков на другом языке через
механизм обновления (`update.py … --language en`, [§6.4](#64-обновление)). Файлы классов `seeded`
и `project`, а также проектная часть `block`-файлов автоматически не переводятся.

**Возможное развитие:** разделить «язык инструкций для агента» и «язык документации». Слабые и китайские
модели, как правило, точнее следуют инструкциям на английском.

## 6. Жизненный цикл

### 6.1. Инициализация нового проекта

```
git clone <шаблон> my-project
cd my-project
./init.sh      # на Windows: init.cmd
```

Или открыть Агента в папке и попросить инициализировать проект: `AGENTS.md` шаблона направит его
в `setup/INIT.md`.

Шаги:

1. **Bootstrap:** найти или скачать uv ([§10.2](#102-uv-внутри-проекта)).
2. **Проверка:** это свежий клон шаблона без локальных изменений. Init предупреждает, если версия — `-dev`
   или HEAD не совпадает с тегом релиза ([§5.4](#54-хостинг-и-версии)).
3. **Параметры:** имя проекта, язык, профиль, модули, агенты на этой машине, ресурсы. Собирает их агент
   по `setup/INIT.md`, либо они передаются флагами при неинтерактивном запуске.
4. **Сборка:** модули профиля копируются в корень, переводимые файлы ставятся на выбранном языке,
   подставляются параметры.
5. **Удаление инсталлятора:** `setup/`, `payload/`, `init.*`, `README.md`, `README.en.md`, `CHANGELOG.md`
   и `AGENTS.md` шаблона. `README.md` и `AGENTS.md` заменяются файлами из payload.
6. **`agentic.lock`:** URL шаблона, версия, коммит, язык, профиль, модули, хэши `managed`-файлов.
7. **Новый git:** удалить `.git` шаблона, выполнить `git init` (ветка `master`), перенести локальные `user.*` клона
   (identity, ключ подписи), применить настройки git ([§7.4](#74-настройки-git)), сделать первый коммит
   `agentic: init from template vX.Y.Z`. В коммит попадают явные пути — файлы payload и lock
   (`git add -f`: глобальный excludes пользователя не выкинет их молча); остатки папки шаблона (локальный
   `CLAUDE.md`, `.obsidian/`, настройки IDE) не коммитятся. Шаг деструктивный и выполняется только после
   подтверждения.
8. **Настройка машины** ([§6.3](#63-новая-машина)).
9. **Содержательная часть (Агент):** проектная часть `AGENTS.md`, каталог ресурсов, первые Entities.

### 6.2. Обёртывание существующих проектов (adopt)

Это инициализация плюс перенос того, что уже есть:

- Существующие репозитории **клонируются заново** в `Resources/`, а не перемещаются. Если человек называет
  локальную копию, `tb resources add` записывает в каталог её `origin` (каталог общий, локальный путь
  работает только на одной машине) и предупреждает о незакоммиченном, незапушенном и stash в старой копии.
  Если upstream недоступен, свежий клон делается из самой копии (`tb resources clone <name> --from <путь>`,
  при `add --clone` — автоматически), а `origin` выставляется на upstream. Перемещение меняет абсолютный
  путь, и всё, что к нему привязано (история и память агентов, настройки IDE), отвалится. Старая копия
  остаётся, пока миграция не закончена.
- Клон шаблона внутри другого Agentic Project (например, ресурс `Resources/agentic-project-template`)
  init не превращает в проект: он отказывается, если выше по дереву есть `.agents/agentic.lock`.
- `AGENTS.md`, `CLAUDE.md` и `.claude/` внутри репозиториев остаются на месте: они принадлежат
  репозиторию и его команде. Инструкции ресурса агент читает по правилу из `AGENTS.md`, а **настройки**
  ресурса (`.claude/settings.json`, `.mcp.json`, `.codex/`, хуки, skills) агент, запущенный из корня
  проекта, не загружает. `tb resources status` и `tb agents doctor` их перечисляют: нужное проекту
  переносится в `.agents/`.
- Личные знания собираются в `Knowledge/`: встроенная память агентов (например,
  `~/.claude/projects/<путь>/memory/`), заметки, личные инструкции. Агент раскладывает их по типам,
  человек подтверждает.
- **Отложенный adopt.** Большой проект (много репозиториев, накопленная память и заметки) за одну сессию
  не обернуть. Init тогда делает только каркас, `AGENTS.md` и главные ресурсы, а ресурсы и личные знания
  переносятся отдельным этапом по задаче в `Knowledge/Tasks/`. Порядок adopt агент записывает в задачу:
  `setup/INIT.md` init удаляет.
- **Тот же путь.** Если новый проект должен занять путь старого, старую папку переименовывают целиком
  (`app` → `appOld`). Это не противоречит запрету перемещать копии: в `Resources/` по-прежнему
  клонируется заново, а старый проект остаётся целым, только по другому пути. Привязанное к абсолютному
  пути переносится вручную, до init: каталог Claude Code `~/.claude/projects/<путь>/` переименовывается
  под новый путь старой копии (иначе её история и память достанутся новому проекту), `includeIf "gitdir:…"`
  с файлом внутри старой папки — файл выносится наружу, сессии Codex (cwd внутри файлов) — только в архив,
  настройки IDE — заново. Порядок — `setup/INIT.md` §6.2.

### 6.3. Новая машина

`git clone <репозиторий проекта>`, затем `Toolbox/tb setup`:

- скачать uv и Python в `Runtime/`;
- создать адаптеры выбранных агентов (`tb agents link`);
- применить настройки git и Obsidian (если модуль включён);
- предложить склонировать ресурсы из каталога.

Та же команда восстанавливает среду после удаления `Runtime/` и подключает нового агента.

### 6.4. Обновление

Запускается изнутри проекта skill-ом `agentic-update`. Skill намеренно тонкий: вся логика обновления
берётся из **свежей** версии шаблона, поэтому обновляется и сам механизм обновления.

1. **Предусловия:** корневой репозиторий чистый, незакоммиченные Знания закоммичены.
2. **Загрузка:** `tb update fetch` клонирует последний релиз шаблона (URL из `agentic.lock`, [§5.4](#54-хостинг-и-версии))
   в `Runtime/update/<версия>/`. Если новее установленного релиза нет, обновление на этом заканчивается.
3. **Инструкция:** Агент выполняет `setup/UPDATE.md` из свежей копии.
4. **План:** `update.py plan` раскладывает файлы по статусам:
   - `managed` без локальных изменений — заменить;
   - `managed` с локальными изменениями — конфликт;
   - новые и удалённые файлы;
   - миграции между версиями.
5. **Оценка:** Агент читает `CHANGELOG.md` между версиями и показывает человеку, что меняется, какие риски
   (особенно миграции Знаний и конфликты) и что нужно сделать.
6. **Подтверждение** человеком.
7. **Применение** в ветке `agentic/update-<версия>`: файлы, миграции, `tb kb lint`, `tb agents link`,
   `tb agents doctor`.
8. **Фиксация:** коммит `agentic: update to vX.Y.Z` с тезисами, обновление `agentic.lock`. Слияние — после
   подтверждения, откат — средствами git.
9. **Очистка** `Runtime/update/`.

Формат Знаний меняют только детерминированные идемпотентные скрипты из `setup/migrations/`. Переводимые
файлы обновляются на языке проекта из `agentic.lock`.

**Состав проекта** меняется тем же механизмом: `plan`, `diff` и `apply` принимают `--add-module`,
`--remove-module`, `--language`, `--profile`. Новые файлы модуля получают статус `add`, файлы удаляемого
модуля — `remove` (изменённые локально — конфликт), смена языка или профиля выглядит как изменение
шаблона: неизменённые файлы обновляются, изменённые дают конфликт. Без нового релиза — из копии
установленной версии (`tb update fetch --ref v<установленная>`).

## 7. Git

### 7.1. Один корневой репозиторий

Корень проекта — git-репозиторий.

- **Отслеживаются:** `AGENTS.md`, `README.md`, `.agents/`, `Knowledge/`, `Toolbox/`, `Resources/README.md`,
  `Resources/resources.toml`, служебные файлы git.
- **Не отслеживаются:** содержимое `Resources/*` (у ресурсов свои репозитории), `Runtime/`, выходы адаптеров,
  `Knowledge/.obsidian/`, `.env*`, мусор ОС и редакторов.

Remote добавляется по желанию: личный бэкап или общий репозиторий команды.

### 7.2. Коммиты Агентом

- Только по команде или явной просьбе.
- Только явные пути; `git add -A` и `git add .` запрещены.
- Формат: `<scope>: <суть>`, в теле — ключевые тезисы изменений.
  Scopes: `knowledge`, `agents`, `toolbox`, `resources`, `agentic` (init и update).
- Перед коммитом срабатывает `pre-commit` из `.agents/git-hooks/`: `tb kb lint --staged` и поиск
  секретов в индексируемых файлах. Обе проверки смотрят на то, что войдёт в коммит (индекс git):
  неотслеживаемые и неиндексированные черновики коммит не блокируют, а сломанная проиндексированная
  заметка не проходит, даже если на диске её уже исправили.

### 7.3. Репозитории ресурсов

Коммиты в ресурсы делаются внутри них (`git -C Resources/<name> …`). Код ресурсов в корневой репозиторий
не попадает.

### 7.4. Настройки git

Ставит `tb setup`:

- `core.hooksPath=.agents/git-hooks`;
- `core.quotePath=false` — иначе кириллица в выводе git превращается в `\320\227…` и сбивает агентов;
- на Windows — `core.longpaths=true`.

## 8. Ресурсы

`Resources/resources.toml` — каталог всех известных ресурсов проекта, хранится в git. У конкретного человека
может быть склонирован любой поднабор.

```toml
[[resource]]
name = "api"                         # имя каталога в Resources/
kind = "git"                         # git | folder
url = "git@github.com:org/api.git"
branch = "main"
description = "Бэкенд API"
entity = "Knowledge/Entities/api.md"
agent_settings_reviewed = [".mcp.json"]   # разобранные настройки агентов ресурса (необязательно)
```

- `tb resources status` — что склонировано, текущая ветка, есть ли изменения.
- `tb resources clone <name>`, `tb resources add <url> [--entity <путь>]`.
- `tb resources set <name> <поле>=<значение>…` — точечная правка записи: меняются только строки нужных
  ключей внутри её `[[resource]]`, остальной текст и комментарии остаются. Пустое значение удаляет поле,
  `name` не меняется, `agent_settings_reviewed` задаётся через запятую. Итог проверяется разбором TOML
  (и сравнением с ожидаемыми записями) до записи: при ошибке файл не меняется. Для `entity` без файла —
  предупреждение.
- **Настройки агентов внутри ресурса** (`.claude/settings.json`, `.mcp.json`, `.codex/…`, `.agents/skills`)
  агент из корня проекта не загружает. `tb resources status` и `tb agents doctor` о них предупреждают,
  кроме путей из `agent_settings_reviewed` — их человек разобрал (нужное перенёс в `.agents/`). Новые пути
  снова дают предупреждение с готовой командой `tb resources set … agent_settings_reviewed=…`.
- Если задаче нужен несклонированный ресурс, Агент предлагает его склонировать.
- Работая внутри ресурса, Агент читает его собственные `AGENTS.md`/`CLAUDE.md`, если они есть.
  Вложенные инструкции разные агенты подхватывают по-разному, поэтому это правило записано явно.
- Задача хранит, какие ресурсы и ветки она затрагивает (поле `resources`).
- **Видимость для поиска:** `Resources/*` игнорируется корневым git, а ripgrep уважает `.gitignore`.
  Лечится разрешающим правилом `!/Resources/*` в `.ignore` ([§16](#16-открытые-вопросы), вопрос 1).
  Ограничения, записанные в `Resources/README`: вложенный репозиторий внутри ресурса, перечисленный в его
  `.gitignore`, ripgrep от корня не видит — его возвращает точечное правило `!/Resources/<ресурс>/<путь>/`
  в проектной части `.ignore` корня, иначе ищем `rg --no-ignore` или `git -C <репозиторий> grep`; поиск,
  учитывающий только `.gitignore` (`grep` оболочки Claude Code — обёртка ugrep), не видит `Resources/`
  вовсе. Пустой результат такого поиска — не доказательство отсутствия.
- **IDE не индексируют ресурсы.** В ресурсах лежат целые репозитории, а в `Runtime/` — uv, Python и кэши.
  Если IDE их индексирует, она тормозит, а поиск засоряется дубликатами. При этом `.gitignore` JetBrains
  для индексации не учитывает, а поиск VS Code читает `.ignore` и видит `Resources/`. Поэтому `tb ide setup`
  (вызывается из `tb setup`) на каждой машине исключает `Resources/` и `Runtime/`:
  - JetBrains — `excludeFolder` в модуле `.idea/*.iml`, корень содержимого которого — корень проекта.
    Если `.idea/` нет, команда пишет минимальный проект: `modules.xml` и `<имя>.iml` типа `WEB_MODULE`.
    Исключение действует с первого открытия проекта.
  - VS Code — `search.exclude` и `files.watcherExclude` в `.vscode/settings.json`. Файл с комментариями
    (JSONC) не переписывается: команда подсказывает, что добавить вручную.

  Папки остаются видимыми, файлы ресурсов открываются и правятся. Ресурс разрабатывают, открыв его
  каталог отдельным проектом IDE. `.idea/` и `.vscode/` в git не попадают.

## 9. Знания

### 9.1. Правила

- Храним только то, что нельзя восстановить из Ресурсов и истории git.
- Храним только живое. Устаревшее исправляем на месте, отжившее удаляем, а прежние версии остаются
  в истории git. Поэтому терминальных статусов («заменено», «устранено», «отказались») нет: такие заметки
  засоряли поиск и ревью, а их история и так есть в git.
- Одна заметка — одна тема. Сначала ищем существующую и обновляем её, а не плодим дубликаты.
- Относительные даты превращаем в абсолютные.
- Имена файлов — латиница, lowercase kebab-case. Заголовок и текст — на языке проекта.
- Ссылки — относительные markdown-ссылки: их одинаково понимают агенты, IDE, GitHub и Obsidian.
  Ссылка на ещё не написанную заметку — с title `"pending"` (`[текст](путь.md "pending")`): это штатная
  отложенная ссылка, а не битая (§9.7).
- Никаких секретов и реальных данных клиентов и пользователей (выгрузок, персональных данных).
- Индекс не ведётся руками: `tb kb index` генерирует его из frontmatter.
- Пишет в Знания основной Агент; коммит — по команде.

### 9.2. Общий frontmatter

```yaml
---
type: gotcha          # decision | entity | example | gotcha | plan | task
title: Заголовок на языке проекта
description: Одна строка — по ней ищут и решают, открывать ли заметку
status: active        # допустимые значения зависят от типа; у gotcha и example поля нет
created: 2026-10-08
verified: 2026-10-08  # когда последний раз сверено с реальностью
tags: []
aliases: []           # синонимы на русском и английском для поиска
resources: []         # имена из resources.toml: name, name/подпуть, любое из них с @branch
---
```

Ключи и значения перечислений — латиницей. Схему проверяет `tb kb lint`.

`resources`: имя ресурса — всё до первого `/` (ветка после `@` сама может содержать `/`), остальное —
подпуть внутри ресурса (`api/src/billing`). Заметки обычно касаются модуля, а не всего репозитория, и
подпуть сужает и поиск, и ревью по ресурсу. `tb kb search --resource api` находит и `api`, и `api/…`;
`--resource api/src` — только этот подпуть и вложенные.

### 9.3. Типы заметок

| Тип | Что хранит | Статусы | Срок жизни |
|---|---|---|---|
| Decisions | Архитектурные решения (ADR): контекст, решение, отвергнутые альтернативы, последствия | `proposed`, `accepted` | Пока решение действует |
| Entities | Карточка сущности: назначение, где лежит в Ресурсах, связи, неочевидные инварианты, владельцы. Не пересказ кода | `active`, `deprecated` (выводится, но ещё есть) | Пока сущность жива |
| Examples | Переиспользуемые примеры и шаблоны — пассивный справочник (процедуры оформляются как skills) | — | Пока актуальны |
| Gotchas | Симптом, причина, обход, как проверить актуальность; поле `applies_to: [node@22]` | — | Пока жива причина |
| Plans | Идеи, отложенное, обнаруженное по ходу работы | `idea`, `ready` | До превращения в задачу или отказа |
| Tasks | Спецификация текущей задачи: цель, детали, решения по ходу, прогресс, итоги для Знаний | `active`, `blocked`, `done` | До сбора итогов |

Конец срока жизни — удаление заметки. Заменённое решение удаляют, а причину замены записывают в новое.
Отвергнутый план удаляют; важную причину отказа оформляют решением. Устранённые грабли, неактуальный
пример и карточку выведенной сущности тоже удаляют. До 0.2.0 для этого были статусы `superseded`
(+ `superseded_by`), `resolved`, `outdated` и `dropped`. Теперь `tb kb lint` предупреждает о них, а
`tb kb stale` показывает такие заметки как кандидатов на удаление. Миграция 0.2.0 только убирает
`status: active` у gotcha и example, а удалять заметки решает человек.

Решения, принятые внутри задачи, живут в задаче и уходят вместе с ней. В Decisions попадают только те,
что переживают задачу.

Задача — файл `Tasks/<slug>.md`. Если нужны артефакты — папка `Tasks/<slug>/` с основной заметкой `index.md`.

### 9.4. Жизненный цикл

```
Plans (idea) ──► Tasks (active) ──► done ──► сбор итогов ──► удаление задачи
                                                 │
                             Decisions / Gotchas / Entities / Examples
```

Удалённая задача остаётся в истории git.

### 9.5. Ревью

Ревью — два skill с явными границами, целью и критериями приёмки. Оба запускаются по просьбе или по
напоминанию:

- `kb-review` — Decisions, Entities, Gotchas, Examples, Tasks. Каждой заметке выносится один вердикт:
  `keep`, `fix`, `shrink`, `merge`, `delete` или `ask`. Без доказательства вердикта нет. Доказательство —
  то, что человек может проверить сам: путь и строка в ресурсе, версия из lock-файла, коммит, вывод
  проверки без побочных эффектов. Если доказательства нет, вердикт — `ask`. Заметки разбиваются на пачки
  по ресурсу, а пачки параллельно проверяют субагенты `kb-auditor`; без субагентов ревью идёт
  последовательно по тем же правилам. Основной Агент сводит вердикты, проверяет пересечения между пачками
  и показывает отчёт. Применяется только то, что подтвердил человек. Итог — `tb kb lint` без ошибок,
  а в `tb kb stale` остаются только заметки с вопросами.
- `plan-review` — бэклог Plans. Вердикты: `ready`, `refine`, `to-task`, `merge`, `delete`, `ask`.
  Проверяются критерии готовности и пересечения с активными задачами, а человеку предлагается порядок
  работ.

`kb-auditor` правила не дублирует: он читает их из `SKILL.md` того skill, который его вызвал. Поэтому
критерии меняются в одном месте.

### 9.6. Obsidian

Корень хранилища — `Knowledge/`. Каталог `.obsidian/` не хранится в git. Модуль `obsidian` на каждой машине
пишет минимальную конфигурацию:

- markdown-ссылки вместо `[[wikilinks]]`;
- относительные пути;
- папка шаблонов `_templates`.

Шаблоны общие для Obsidian и `tb kb new`.

### 9.7. Проверки: `lint` и `verify`

`tb kb lint` — ошибки блокируют коммит (pre-commit запускает `lint --staged`), предупреждения нет.

- **Ссылки.** Цели нет — ошибка `broken link`. Цель внутри несклонированного ресурса не проверяется,
  внутри склонированного — предупреждение.
- **`--staged`** проверяет то, что войдёт в коммит: заметки и `resources.toml` из индекса git, ссылки
  резолвятся по индексу. Цель есть на диске, но не в индексе — предупреждение «not staged yet», а не
  ошибка: параллельные сессии в одном дереве коммитят свои заметки раздельно. Цели нет и на диске —
  ошибка.
- **Отложенная ссылка** — title `"pending"` (в любых кавычках или скобках, которые допускает Markdown).
  Пока цели нет — предупреждение; цель появилась — подсказка убрать title. `tb kb stale` показывает
  такие заметки как кандидатов на доработку, `tb kb related` помечает ссылки `[pending]`. Title выбран
  потому, что его понимают все рендереры (он просто становится всплывающей подсказкой), а заметка
  остаётся обычным Markdown.
- **`resources`.** Имя — из каталога (иначе ошибка). Подпуть проверяется, только если ресурс склонирован:
  его нет — предупреждение.
- **Каталог.** `entity` ресурса указывает на несуществующий файл (путь от корня проекта) — ошибка
  в `Resources/resources.toml`; в `--staged` файл на диске, но не в индексе — предупреждение. Карточка
  `Entities/*.md` перечисляет в `resources` ресурс (без подпути) с пустым `entity` — подсказка заполнить
  его (`tb resources set <name> entity=<path>`).
- **`AGENTS.md`** — бюджет только проектной части (§12.1).

`tb kb verify <путь|slug>…` фиксирует, что заметку сверили с реальностью: ставит `verified: <сегодня>`
(`--date` — другую дату) и линтует эти заметки; код 1 при ошибках, неизвестная заметка — ошибка, остальные
всё равно обрабатываются. Строка `verified:` заменяется (комментарий в ней сохраняется) или вставляется
после `created:`; остальной файл не меняется ни на байт — YAML не пересериализуется, чтобы не терять
порядок ключей, кавычки и комментарии. `--dry-run` только показывает.

## 10. Toolbox и среда выполнения

### 10.1. Назначение

Toolbox — инструменты проекта и слой независимости от хостовой системы.
Требования к хосту: **Агент, git и доступ в интернет при первом запуске**. Всё остальное Toolbox привозит сам.

### 10.2. uv внутри проекта

- Инструменты пишутся на Python. Зависимости объявляются в самом скрипте (PEP 723), версии фиксируются
  (`requires-python`, `exclude-newer`).
- `Toolbox/tb` (POSIX sh, включая Git Bash) и `Toolbox/tb.cmd` (cmd и PowerShell) — единственное место
  с bootstrap-логикой:
  1. взять uv из PATH, если версия подходит;
  2. иначе скачать закреплённую версию в `Runtime/tools/uv/` и проверить sha256. На Windows 10+ хватает
     встроенных `curl.exe`, `tar.exe` и `certutil`; PowerShell, если понадобится, вызывается только
     с `-ExecutionPolicy Bypass`;
  3. выставить, если не заданы пользователем, `UV_PYTHON_INSTALL_DIR=Runtime/tools/python`,
     `UV_PYTHON_BIN_DIR=Runtime/tools/python-bin`, `UV_CACHE_DIR=Runtime/cache/uv` и
     `UV_PYTHON_PREFERENCE=only-managed`. Без `UV_PYTHON_BIN_DIR` uv кладёт ссылку на Python
     в `~/.local/bin` — это проверено на практике;
  4. запустить инструмент через `uv run`.
- **Хуки агентов** (`tb hook …`) никогда не блокируют агента: код возврата всегда 0 (код 2 у Claude Code
  отклоняет промпт), без загрузок (офлайн, без скачивания Python). Пока `tb setup` не подготовил
  `Runtime/`, хук молча ничего не делает — первый промпт после сброса среды не ждёт загрузку.
- `TB_ROOT` — переопределение корня для `tb` самого шаблона (разработка, init). Корень должен содержать
  `.agents/agentic.lock` или `setup/VERSION`; `tb` развёрнутого проекта унаследованный `TB_ROOT`
  игнорирует с предупреждением. Без `TB_ROOT` копия `tb` в `payload/modules/core/Toolbox/` отказывается
  работать (хук молча выходит с 0): иначе она создала бы `Runtime/` внутри payload.
- Глобально ничего не ставится, права администратора не нужны. Удаление `Runtime/` удаляет среду,
  следующий вызов `tb` восстанавливает её.
- Прокси и зеркала: стандартный `HTTPS_PROXY`, `UV_PYTHON_INSTALL_MIRROR`, переопределяемый URL загрузки uv.
- `init.sh` и `init.cmd` шаблона используют ту же bootstrap-логику.

### 10.3. Состав

- `Toolbox/agentic/` — управляемые инструменты шаблона: `kb`, `agents`, `resources`, `update`, `setup`,
  `obsidian`, `hook`.
- Остальное — инструменты проекта. Запускаются через `tb run <script>` и описываются в `Toolbox/README.md`.

### 10.4. Соглашения для вывода

- Пути — относительно корня проекта, через `/`.
- По умолчанию — компактный текст, `--json` — для машинной обработки.
- Пустой результат сообщается явно.
- При ошибке — ненулевой код возврата.
- Сообщения — на английском, независимо от языка проекта ([§5.5](#55-языки)).

### 10.5. Docker (модуль `devcontainer`)

Docker не основной способ запуска Toolbox:

- требует установки с правами администратора и виртуальную машину (Docker Desktop платный для крупных компаний);
- добавляет задержку к каждому вызову, что критично для хуков;
- на Windows не может создать адаптеры для нативных агентов;
- усложняет пути, права на файлы и git.

Зато в контейнере удобно запускать **самого Агента**: песочница для автономного режима, изоляция агентов
и моделей с меньшим доверием, полная воспроизводимость. Модуль `devcontainer` добавляет `.devcontainer/`
с CLI агентов и uv. Toolbox внутри работает так же, как на хосте.

## 11. Агенты и адаптеры

### 11.1. Уровни возможностей

| Уровень | Агент умеет | Как работает система |
|---|---|---|
| 0 | Читать `AGENTS.md` и выполнять команды | Протокол записан текстом в `AGENTS.md`. Процедуры: «найди подходящий skill в `.agents/skills/` и прочитай `SKILL.md`». Инструменты — `tb` |
| 1 | Нативные skills | Skills подхватываются автоматически |
| 2 | Субагенты | Библиотекарь и другие работают в изолированном контексте |
| 3 | Хуки | Автонапоминания, подстановка результатов `kb` |

Уровень 0 обязан работать полностью: это гарантия для новых и более слабых агентов.

### 11.2. Канонические форматы

- **Инструкции** — `AGENTS.md`.
- **Skills** — `.agents/skills/<name>/SKILL.md` по стандарту Agent Skills: имя каталога совпадает с `name`,
  kebab-case; `scripts/`, `references/`, `assets/` — по необходимости.
- **Отдельного `commands/` нет**: любая процедура оформляется как skill. В Claude Code пользовательские
  команды объединены со skills, Codex вызывает skills напрямую.
- **Субагенты** — `.agents/agents/<name>.md`, frontmatter без привязки к конкретному агенту:

  ```yaml
  ---
  name: librarian
  description: …
  model: fast        # fast | balanced | strong — адаптер переводит в конкретную модель
  tools: read-only   # read-only | edit | shell
  ---
  ```

- **Хуки** — `.agents/hooks/hooks.toml` с абстрактными событиями `session-start`, `prompt-submit`,
  `before-tool`, `after-tool`, `stop`. Команда хука всегда `Toolbox/tb hook <name>`. События, которые агент
  не поддерживает, адаптер пропускает с предупреждением.
- **MCP** — `.agents/mcp.toml`.
- **Разрешения** — `.agents/permissions.toml` (seeded: ставится с закомментированными примерами и дальше
  принадлежит проекту):

  ```toml
  [[command]]                          # shell-команда, сопоставляется по префиксу argv
  prefix = ["git", "push", "--force"]  # непустой список слов
  decision = "deny"                    # deny | ask | allow
  reason = "Переписывает общую историю"  # необязательно; Codex показывает как justification

  [claude]                             # правила только для Claude Code, копируются как есть
  deny = ["Read(./secrets/**)"]
  ask = []
  allow = []
  ```

  Claude Code получает `Bash(<слова через пробел>)` и `Bash(<слова> *)`, Codex — `prefix_rule` по словам
  argv. Слова склеиваются как есть, без shell-кавычек: Claude сравнивает текст правила, и `rm -rf '~'`
  не совпал бы с `rm -rf ~`. Поэтому слово с пробельным символом, кавычкой или `*` недопустимо: `*`
  для Claude — подстановка, для Codex — литерал, агенты разошлись бы. Такие правила — в `[claude]`.
  Туда же — правила с шаблоном в середине (`git -C * push`, `curl * | sh`): Codex `prefix_rule` сопоставляет
  argv только с начала, для Codex они не выражаются.

  Файл не разбирается целиком (ошибка TOML, `command` не массив таблиц, `claude` не таблица) — ошибка:
  `tb agents link` оставляет сгенерированные файлы с разрешениями (`.claude/settings.json`,
  `.codex/rules/project.rules`) как есть и возвращает ненулевой код, `doctor` показывает ✗. Иначе link
  молча снял бы все запреты. Предупреждения об общих источниках `.agents/` печатаются один раз за запуск,
  а пропуск `[claude]` в Codex — ожидаемое ограничение: `note` в `link`, информационная строка в `doctor`.

  Ошибки отдельных правил (неизвестный `decision`, пустой или не строковый `prefix`, недопустимое слово
  в `prefix`, неизвестные ключи) — предупреждение при `tb agents link`/`doctor`, ошибочное правило
  пропускается, остальные применяются.
  Личные правила — в локальных настройках агента (`.claude/settings.local.json`, `~/.codex/rules/`).

### 11.3. Манифест адаптера

`.agents/adapters/<agent>/adapter.toml` описывает, как агент видит систему. Сокращённый манифест Claude
(полная версия — в payload):

```toml
name = "claude"
title = "Claude Code"
tier = 3
outputs = ["/.claude/", "/.mcp.json", "/CLAUDE.md"]   # должны быть в управляемом блоке .gitignore

[instructions]
target = "CLAUDE.md"                     # генерируется: <!-- … --> + @AGENTS.md
import = "AGENTS.md"

[skills]
mode = "link"                            # native | link | none
target = ".claude/skills"
granularity = "per-skill"                # .claude/skills/<name> → .agents/skills/<name>

[subagents]
target = ".claude/agents"
models = { fast = "haiku", balanced = "sonnet", strong = "opus" }
tools = { read-only = "Read, Grep, Glob", shell = "Read, Grep, Glob, Bash", edit = "Read, Grep, Glob, Bash, Edit, Write" }

[hooks]
target = ".claude/settings.json"
command = '"$CLAUDE_PROJECT_DIR"/Toolbox/tb hook {name} --agent claude'
events = { session-start = "SessionStart", prompt-submit = "UserPromptSubmit", before-tool = "PreToolUse", after-tool = "PostToolUse", stop = "Stop" }

[permissions]
target = ".claude/settings.json"
allow = ["Bash(Toolbox/tb kb search *)", "Bash(Toolbox/tb kb show *)", "Bash(Toolbox/tb version)", …]  # только читающие
# + правила .agents/permissions.toml; у Codex — только target = ".codex/rules/project.rules"

[memory]
target = ".claude/settings.json"
disable = true                           # autoMemoryEnabled = false

[mcp]
target = ".mcp.json"                     # создаётся, только если в .agents/mcp.toml есть серверы
```

Сгенерированные файлы не содержат абсолютных путей: Claude получает корень из `$CLAUDE_PROJECT_DIR`,
а команда хука Codex (`{tb_find}`) поднимается от текущего каталога до папки с `.agents/agentic.lock`.
Поэтому они переживают перенос папки проекта, работают в devcontainer и из подкаталога вроде
`Resources/<name>`. Исключение — `commandWindows` Codex: относительный `Toolbox\tb.cmd`, сессия должна
начинаться в корне проекта ([§16](#16-открытые-вопросы), вопрос 3).

Генераторы форматов лежат в `Toolbox/agentic/adapters/`.

### 11.4. Команды

- `tb agents link [<agent>…]` — создать ссылки и сгенерировать конфиги на этой машине (идемпотентно).
- `tb agents doctor` — проверить, что всё на месте и актуально.
- `tb agents list` — доступные адаптеры и их уровни.

Ссылки на каталоги — symlink, а на Windows без прав — junction. Ссылки на файлы не используются.

### 11.5. Расширение

Новый агент — это новый каталог в `.agents/adapters/` и, при необходимости, генератор. Ядро не меняется,
новые адаптеры приходят в проекты обычным обновлением.

Китайская или опенсорсная **модель** внутри уже поддержанного агента (через совместимый API) адаптера
не требует. Для неё важны надёжность уровня 0 и инструмент `kb`.

### 11.6. Стартовые адаптеры

- **claude** — уровень 3.
  - Генерируется `CLAUDE.md` из одной строки `@AGENTS.md` (в git не попадает). Свежие версии Claude Code
    читают `AGENTS.md` сами, только если нет `CLAUDE.md`, старые — только `CLAUDE.md`; импорт работает
    с обеими, и ни одна версия не останется без инструкций проекта. Заметки только для Claude — в
    `.claude/CLAUDE.md` или `CLAUDE.local.md`. Ручной симлинк `CLAUDE.md → AGENTS.md` `tb agents link`
    заменяет файлом; чужой `CLAUDE.md` без импорта `doctor` считает ошибкой.
  - Skills видит через ссылку на каждый skill: `.claude/skills/<name>` → `.agents/skills/<name>`. Такие
    ссылки документированы, а ссылка на весь каталог — нет.
  - Генерируются `.claude/settings.json` (авто-память выключена через `autoMemoryEnabled: false`,
    разрешения на читающие команды `tb`, хуки), `.claude/agents/*.md` и `.mcp.json`.
  - Разрешения `.claude/settings.json` = `allow` шаблона из `adapter.toml` + `.agents/permissions.toml`:
    `prefix` → `Bash(<cmd>)` и `Bash(<cmd> *)` (точная команда и с аргументами) в `deny`/`ask`/`allow`,
    плюс правила `[claude]` как есть; без дублей.
  - Личные настройки Claude — в `.claude/settings.local.json`: генератор его не трогает.
- **codex** — уровень 3.
  - `AGENTS.md` и `.agents/skills` читает нативно, ссылки не нужны.
  - Генерируются `.codex/config.toml` (MCP, `[features] memories = false`), `.codex/hooks.json`,
    `.codex/agents/*.toml` и `.codex/rules/project.rules`.
  - Правила `[[command]]` из `.agents/permissions.toml` → Starlark `prefix_rule(pattern=[…],
    decision=…, justification=…)`: deny → `forbidden`, ask → `prompt`, allow → `allow`. Файл пишется,
    только если правила есть. `[claude]` пропускается с предупреждением. Codex читает проектные rules
    только в доверенном проекте; в 2026 rules помечены экспериментальными. Проверка —
    `codex execpolicy check --rules .codex/rules/project.rules -- <cmd>`; после правки Codex перезапускают.
  - Уровень `tools = shell` даёт субагенту `workspace-write`: `tb` пишет кэш в `Runtime/`, и в read-only
    песочнице не работал бы. «Только чтение» библиотекаря обеспечивают его инструкции.
  - Проектный `.codex/` читается только для доверенных (trusted) проектов. Новые хуки человек один раз
    одобряет в `/hooks`.

## 12. Контекст и библиотекарь

### 12.1. Бюджет старта

При старте сессии в контекст попадают `AGENTS.md` целиком и описания всех skills и субагентов (плюс MCP,
если подключён). Поэтому:

- `AGENTS.md` — не больше ~1500 токенов: карта, правила, ссылки. Бюджет делится на две части:
  - блок шаблона (`agentic:begin`…`agentic:end`) — ≤ 900 с самым длинным профилем. Его проект не
    контролирует, поэтому проверяет его unit-тест шаблона, а не `tb kb lint`;
  - проектная часть (всё вне блока) — ≤ 800. Превышение — предупреждение `tb kb lint` с числами и советом
    вынести подробности в Знания или skills. Нет маркеров — весь файл считается проектной частью
    с бюджетом 1500, как раньше.

  Оценка грубая (`estimate_tokens`: ~4 символа ASCII или ~2,5 кириллических на токен), но одна и та же
  для теста и lint;
- skills — немного и с точными описаниями;
- Знания при старте не читаются.

Скелет `AGENTS.md`:

1. О проекте — 2–3 строки (проектная часть).
2. Карта каталогов (управляемый блок).
3. Правила (управляемый блок):
   - память — только `Knowledge/`, встроенную память агента не использовать;
   - временные файлы — в `Runtime/`;
   - коммиты — только по команде;
   - `Resources/*` — отдельные репозитории со своими инструкциями;
   - где лежат skills и как ими пользоваться без нативной поддержки;
   - команды `tb` (на Windows `Toolbox\tb.cmd`).
4. Протокол сессии (управляемый блок).
5. Особенности проекта (проектная часть).

### 12.2. Библиотекарь

Логика живёт в skill `kb-lookup`, так что она переносима. Субагент `librarian` — обёртка для изолированного
контекста. Где субагентов нет, skill выполняется в основной сессии, в крайнем случае хватает `tb kb search`.

**Когда обращаться:**

- перед планированием задачи;
- перед принятием решения;
- при первом касании сущности в сессии;
- когда ошибка кажется знакомой.

**Процесс:** `tb kb search` → чтение лучших совпадений → сверка утверждений с Ресурсами (версии в lock-файлах
зависимостей, существование файлов и функций) → ответ.

**Формат ответа:**

```
Ответ: …
Источники: Knowledge/Gotchas/….md, …
Проверка: confirmed | stale? | unverifiable (почему)
Предложения по Знаниям: … (если что-то устарело)
```

Если ничего не найдено, это сообщается явно.

Библиотекарь только читает, правки Знаний вносит основной Агент. Пути в ответе обязательны: если пересказ
потерял нюанс, основной Агент откроет оригинал.

### 12.3. Поиск: `tb kb`

| Команда | Назначение |
|---|---|
| `search <запрос>` | BM25 и стемминг Snowball (RU/EN) по `title`, `description`, `aliases`, `tags` и тексту; фильтры `--type`, `--status`, `--resource` |
| `show <путь>` | Заметка целиком |
| `related <путь>` | Ссылки и обратные ссылки |
| `new <type> <slug>` | Новая заметка из шаблона |
| `index` | Индекс из frontmatter |
| `lint` | Схема frontmatter, ссылки, имена файлов, секреты, бюджет `AGENTS.md` |
| `verify <путь\|slug>…` | Отметить сверку (§9.7) |
| `stale` | Кандидаты на перепроверку и отложенные ссылки |

- Индекс строится в памяти: Знаний немного. Кэш в `Runtime/cache/` — если понадобится.
- Интерфейс — CLI, а не MCP: описания MCP-инструментов занимают контекст при старте. MCP-обёртка
  и семантический поиск — позже и опционально.
- Для агентов с хуками: на `prompt-submit` выполняется `tb kb search --brief` по тексту запроса, и в контекст
  попадают только заголовки и пути найденных заметок.

## 13. Протокол сессии и базовые skills

**Протокол:**

- **Старт:** `AGENTS.md`; при необходимости — список активных задач (`tb kb search --type task --status active`,
  только заголовки).
- **Работа:** перед решениями — `kb-lookup`; временные файлы — в `Runtime/`.
- **Завершение:** `wrap-up`.
- **Периодически:** `kb-review`, `plan-review`.

**Базовые skills:**

| Skill | Назначение |
|---|---|
| `kb-lookup` | Библиотекарь: найти и проверить ответ в Знаниях |
| `wrap-up` | Итоги сессии: статус задач, отложенное в Plans, найденные грабли в Gotchas, предложения ADR; предложить коммит |
| `kb-commit` | `tb kb lint --staged` и коммит Знаний с ключевыми тезисами; хук pre-commit не обходится, ссылка на заметку вне коммита — в коммит или отложенная (`"pending"`) |
| `kb-review` | Ревью Знаний: вердикты с доказательствами, проверка пачками через `kb-auditor` ([§9.5](#95-ревью)) |
| `plan-review` | Ревью бэклога Plans ([§9.5](#95-ревью)) |
| `agentic-update` | Обновление проекта из шаблона ([§6.4](#64-обновление)) |

Отдельного списка skills в `AGENTS.md` нет: протокол называет нужные, а описания skills агент и так
получает при старте ([§12.1](#121-бюджет-старта)). Блок шаблона в `AGENTS.md` с самым длинным профилем —
не больше 900 токенов по оценке `tb kb lint`; проверяет unit-тест.

Общее для `kb-review` и `plan-review`:

- отрицательное утверждение («нет в коде», «не используется») доказывает только поиск без учёта
  ignore-файлов по всем затронутым репозиториям, включая вложенные (`rg --no-ignore`, `git -C <путь> grep`):
  обычный поиск может не видеть ресурсы ([§16](#16-открытые-вопросы), вопрос 1);
- пачки — по ресурсу, а при `<ресурс>/<подпуть>` в `resources` — по модулю;
- большой охват (больше ~30 заметок): `kb-auditor` получает путь отчёта
  `Runtime/<skill>/<ГГГГ-ММ-ДД>/<пачка>.md`, пишет туда полный отчёт и отвечает сводкой до 10 строк;
  основной Агент сводит по файлам. Так контекст основной сессии не переполняется. Это единственная
  запись, которую может сделать `kb-auditor`;
- `verified` ставит `tb kb verify <пути>`, а не ручная правка.

Инициализация — это не skill: до неё адаптеры ещё не созданы. Её ведёт инструкция `setup/INIT.md`.

## 14. Кроссплатформенность

Чек-лист:

- Симлинки не коммитятся. Каталоги связываются через symlink или junction, файловых ссылок нет.
- Входы: `.sh` и `.cmd`. PowerShell — только с `-ExecutionPolicy Bypass`.
- `.gitattributes`: `* text=auto eol=lf`, для `*.cmd` и `*.bat` — `eol=crlf`.
- Имена файлов — латиница, kebab-case, без запрещённых в Windows символов и имён (`CON`, `NUL`, …).
  Проверяет `tb kb lint`.
- Настройки git — [§7.4](#74-настройки-git).
- Пути в выводе инструментов — относительные, через `/`.
- Регистр имён каталогов фиксирован.
- Проверка на macOS и Windows — обязательная часть пилота.

## 15. Безопасность

- Секреты не попадают в `Knowledge/`, `Toolbox/` и `.agents/`. `.env*` — в `.gitignore` (кроме
  `.env.example` и подобных), поиск секретов — в pre-commit по всем индексируемым файлам: ключи и токены
  провайдеров, приватные ключи, JWT, `Bearer`, пароли в URL и присваивания вида `password = …`. Общие
  шаблоны отбрасывают плейсхолдеры (`<password>`, `${TOKEN}`, `changeme`, `example`); ложное срабатывание
  помечается `agentic:allow-secret` в той же строке. Это страховка, а не гарантия.
- Агент не обходит pre-commit: ни `--no-verify`, ни `git commit-tree`, ни отключение хука. Правило —
  в блоке шаблона `AGENTS.md` и в `kb-commit`: упавший хук чинят по причине, а не обходят.
- uv скачивается закреплённой версии с проверкой sha256.
- Источник обновлений — только URL из `agentic.lock`. Сменить источник может только человек.
- В `Runtime/` могут оказаться логи с чувствительными данными: он не в git и очищается осознанно.
- Агентов и модели с меньшим доверием запускаем в `devcontainer`.

## 16. Открытые вопросы

1. **Поиск и `Resources/*`.** Проверено:
   - ripgrep 15 видит ресурсы с правилом `!/Resources/*` в `.ignore` корня (вариант `!/Resources/`
     не работает);
   - вложенные репозитории внутри ресурса, перечисленные в его `.gitignore`, правило `!/Resources/*`
     не возвращает: оно действует только на первом уровне. Возвращает точечное правило
     `!/Resources/<ресурс>/<путь>/` в проектной части `.ignore` корня (под блоком шаблона; rg 15.2);
   - `grep` в оболочке Claude Code — обёртка ugrep с `--ignore-files` (учитывает только `.gitignore`):
     от корня проекта он не видит `Resources/` вообще.

   Обход — точечное правило в `.ignore` корня для нужных вложенных репозиториев и правило
   в `Resources/README.md` и skills ревью: пустой поиск — не доказательство, для отрицательных
   утверждений — `rg --no-ignore` или `git -C <репозиторий> grep`. Открыто: встроенные
   Grep/Glob терминального `claude` и поиск Codex.
2. **Worktree и параллельные сессии.** Worktree корневого репозитория не содержит ресурсов, а Claude desktop
   создаёт такие worktree для сессий. Варианты:
   - worktree внутри ресурсов;
   - ссылки на ресурсы при создании worktree;
   - отказ от worktree-режима на уровне корня.
3. **Windows.** `tb.cmd`, `init.cmd`, junction и хуки на Windows написаны, но не запускались. Проверить на пилоте,
   в том числе `$CLAUDE_PROJECT_DIR` с обратными слэшами в хуке Claude (Git Bash) и `commandWindows` Codex,
   который требует запуска сессии из корня проекта.

**Закрытые вопросы:**

- **Хостинг и версии** — [§5.4](#54-хостинг-и-версии).
- **Язык** — [§5.5](#55-языки).
- **Профили v1** — `software` (ресурсы — git-репозитории с кодом) и `generic` (проекты без кода:
  документация, исследования). Они различаются только фрагментом правил в `AGENTS.md`.
- **Codex и Claude Code** — возможности исследованы, см. [§11.6](#116-стартовые-адаптеры) и
  [Приложение А](#приложение-а-проверенные-факты-об-агентах).
- **Пороги устаревания** (дни с `verified`, иначе с `created`):

  | Заметки | Порог |
  |---|---|
  | gotcha | 90 |
  | entity, example | 180 |
  | plan (`idea`, `ready`) | 60 |
  | task (`active`, `blocked`) | 30 |
  | decision (`proposed`) | 30 |

  Задача в статусе `done` попадает в отчёт всегда как ожидающая сбора итогов. Порог можно переопределить
  флагом `tb kb stale --days`.
- **Хуки v1** — только `prompt-submit` → `kb-suggest`: подставляет в контекст заголовки и пути подходящих
  заметок. Напоминание о `wrap-up` на `stop` отклонено: это событие срабатывает после каждого ответа агента.

## Приложение А. Проверенные факты об агентах

Проверено 2026-10-08. Такие факты быстро устаревают — перепроверять при работе над адаптерами.

- Claude Code читает `AGENTS.md`, если в каталоге нет `CLAUDE.md` (с версии 2.1.277, сентябрь 2026).
  Старые версии — только `CLAUDE.md`, поэтому адаптер генерирует `CLAUDE.md` с `@AGENTS.md`.
  [Simon Willison](https://simonwillison.net/2026/Sep/18/thariq-shihipar/),
  [zeli.app](https://zeli.app/story/49760187)
- Codex ищет skills в `.agents/skills` (корень репозитория, рабочий каталог, `~/.agents/skills`).
  [Codex: Agent Skills](https://developers.openai.com/codex/skills)
- Claude Code не сканирует `.agents/skills`, ему нужен `.claude/skills` (через ссылку).
  [kanaries](https://docs.kanaries.net/fr/articles/codex-vs-claude-code-skills)
- Agent Skills — открытый стандарт, его поддерживают Claude Code, Codex, Cursor, Gemini CLI и другие.
  [agentskills.io](https://agentskills.io/)
- Единого формата хуков нет: у каждого агента свой конфиг и свои события.
  [Сравнение систем хуков](https://lilting.ch/en/articles/gemini-cli-hooks-research),
  [Cursor: third-party hooks](https://cursor.com/docs/reference/third-party-hooks)

**Claude Code** ([документация](https://code.claude.com/docs/en/)):

- Авто-память выключается ключом `autoMemoryEnabled: false` в настройках проекта или переменной
  `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (memory.md).
- Skill в `.claude/skills/<name>` может быть ссылкой на каталог в другом месте (skills.md).
- Субагенты: `.claude/agents/<name>.md`, frontmatter `name`, `description`, `tools`, `model`
  (`haiku`, `sonnet`, `opus`, `inherit`, …) (sub-agents.md).
- Хук `UserPromptSubmit` получает JSON с полем `prompt`; stdout при коде 0 добавляется в контекст.
  `$CLAUDE_PROJECT_DIR` доступен. На Windows хуки выполняет Git Bash, если он установлен (hooks.md).
- Пользовательские команды объединены со skills, skill вызывается как `/имя` (skills.md).

**Codex CLI** ([документация](https://learn.chatgpt.com/docs/), бывший developers.openai.com/codex):

- `AGENTS.md` читается по пути от корня git до рабочего каталога; общий лимит — 32 КиБ.
- Skills ищутся в `.agents/skills` во всех каталогах от рабочего до корня репозитория. Ссылки
  поддерживаются, явный вызов — `$имя`.
- Проектный `.codex/config.toml` читается только для доверенных проектов. MCP задаётся в `[mcp_servers.<name>]`,
  память выключена по умолчанию (`[features] memories`).
- Хуки: `.codex/hooks.json`, формат как у Claude, есть поле `commandWindows`. Новый хук нужно одобрить
  в `/hooks`.
- Субагенты: `.codex/agents/<name>.toml` с полями `name`, `description`, `developer_instructions`
  и любыми ключами config (`model_reasoning_effort`, `sandbox_mode`).
- На Windows Codex работает нативно, команды выполняются в PowerShell.
- Пользовательские промпты устарели, вместо них — skills.
