## 1. Назначение и границы

**Agentic Project** — рабочая среда, в которой Агент комфортно работает над всеми Ресурсами проекта.
Проект — это не один репозиторий, а связанное множество: репозитории-ресурсы, Знания о них, инструменты
и инструкции. Набор ресурсов у разных людей в команде может отличаться — это нормально.

**agentic-project-template** — шаблон, из которого такие проекты разворачиваются и через который обновляются.

**Цели:**

- быстро развернуть новый проект или «обернуть» существующие репозитории;
- не зависеть от конкретного Агента: Claude Code и Codex на старте, безболезненное добавление других,
  включая опенсорсные и китайские;
- не зависеть от хостовой системы: macOS, Linux и Windows с первого дня;
- копить Знания внутри проекта под git, а не в системных каталогах агентов (`~/.claude` и т.п.);
- экономить контекст: старт сессии дешёвый, Знания подтягиваются по требованию;
- обновлять проект из свежей версии шаблона силами Агента, под контролем человека;
- поставляться на двух языках: русском (по умолчанию) и английском.

**Не цели v1:**

- регламентировать содержимое Ресурсов;
- политика провайдеров и конфиденциальности данных (отложено);
- специальные механизмы командной синхронизации Знаний (корневой репозиторий можно расшарить как есть);
- семантический (векторный) поиск.

## 2. Термины

| Термин | Значение |
|---|---|
| Шаблон | Репозиторий `agentic-project-template` |
| Проект | Папка, развёрнутая из шаблона; корневой git-репозиторий |
| Ресурсы | То, над чем работаем (`Resources/`), чаще всего — отдельные git-репозитории |
| Знания | Постоянная память проекта (`Knowledge/`) |
| Модуль | Единица payload: набор файлов в раскладке проекта + шаги установки |
| Профиль | Именованный набор модулей под тип проекта |
| Язык проекта | `ru` или `en`; выбирается при init, определяет язык всех переводимых файлов |
| Релиз | Версия шаблона, отмеченная git-тегом `vX.Y.Z` |
| Адаптер | Всё, что нужно конкретному Агенту, чтобы увидеть систему проекта |
| Управляемый файл | Файл, которым владеет шаблон; обновляется при update |
| Библиотекарь | Процедура поиска и проверки ответов в Знаниях (skill + субагент) |

## 3. Принципы

1. **`.agents/` — единственный источник правды** для всего системного. Каталоги конкретных агентов
   (`.claude/`, `.codex/`, …) генерируются и в git не попадают.
2. **Плавная деградация.** Всё работает у агента, который умеет только читать `AGENTS.md` и выполнять
   команды. Нативные skills, субагенты и хуки — улучшение, а не требование.
3. **В Знаниях — только то, что не выводится** из Ресурсов и истории git.
4. **Механику делает скрипт, смысл — Агент.** Детерминированные идемпотентные операции (структура, ссылки,
   конфиги, миграции) — в Toolbox. Интервью, анализ, тексты — в skills.
5. **Дешёвый старт.** При старте в контекст попадают только `AGENTS.md` и описания skills.
6. **Никаких пустых каталогов.** В каждом каталоге лежит README с правилами или шаблоны — это заодно
   инструкция Агенту.
7. **Необратимое подтверждает человек:** инициализацию, обновление, коммиты (по команде или явной просьбе).

## 4. Структура развёрнутого проекта

```
<project>/
├── AGENTS.md                 # точка входа для всех агентов
├── README.md                 # о проекте — для человека
├── .gitignore  .gitattributes  .ignore
├── .agents/                  # системное, источник правды
│   ├── agentic.lock          # происхождение из шаблона, профиль, модули, хэши управляемых файлов
│   ├── skills/               # процедуры (стандарт Agent Skills)
│   ├── agents/               # субагенты в каноническом формате
│   ├── hooks/                # hooks.toml с абстрактными событиями + скрипты
│   ├── git-hooks/            # хуки git (pre-commit: kb lint, поиск секретов)
│   ├── adapters/<agent>/     # манифесты адаптеров
│   ├── mcp.toml              # каноническое описание MCP-серверов
│   └── docs/                 # концепция и справка — читаются по требованию
├── Knowledge/                # хранилище Obsidian
│   ├── README.md             # общие правила Знаний
│   ├── _templates/           # шаблоны заметок (tb kb new + Obsidian)
│   └── Decisions/ Entities/ Examples/ Gotchas/ Plans/ Tasks/   # в каждом — README.md с правилами
├── Resources/
│   ├── README.md             # правила работы с ресурсами
│   ├── resources.toml        # каталог ресурсов проекта
│   └── <name>/               # склонированные ресурсы (не в корневом git)
├── Toolbox/
│   ├── README.md             # индекс инструментов
│   ├── tb  tb.cmd            # единая точка входа
│   ├── agentic/              # инструменты шаблона (управляемые)
│   └── …                     # инструменты проекта
├── Runtime/                  # не в git
└── .claude/  .codex/  …      # генерируемые адаптеры, не в git
```

Состав зависит от профиля и модулей ([§5.3](#53-модули-и-профили)). Имена корневых каталогов фиксированы,
регистр важен.

В `Runtime/` за системой зарезервированы `tools/`, `cache/` и `update/`. Остальная структура — на усмотрение
исполнителя.

## 5. Репозиторий шаблона

### 5.1. Раскладка: setup и payload

```
agentic-project-template/
├── AGENTS.md          # для агента: разработка шаблона или инициализация (→ setup/INIT.md)
├── README.md          # концепция — для человека (русский)
├── README.en.md       # то же на английском
├── CHANGELOG.md       # версии и миграции
├── init.sh  init.cmd  # вход в инициализацию
├── setup/             # инсталлятор, в проект не попадает
│   ├── DESIGN.md      # этот документ
│   ├── INIT.md        # инструкция агенту по инициализации
│   ├── UPDATE.md      # инструкция агенту по обновлению (исполняется из свежей копии шаблона)
│   ├── VERSION
│   ├── init.py  update.py
│   ├── i18n_check.py  # проверка парности переводов
│   ├── profiles/      # профили: какие модули и с какими параметрами
│   └── migrations/    # детерминированные миграции между версиями
└── payload/
    └── modules/<module>/…   # файлы модулей в раскладке проекта; переводимые — парами *.ru.* / *.en.*
```

Шаблон сам не является Agentic Project: генератор и результат не смешиваются. Собственные решения шаблона
живут в этом документе и в `CHANGELOG.md`.

`AGENTS.md` шаблона различает два режима. Если просят развернуть или инициализировать проект, Агент
выполняет `setup/INIT.md`. Иначе он работает над самим шаблоном.

### 5.2. Владение файлами

| Класс | Владелец | Что делает update |
|---|---|---|
| `managed` | шаблон | Перезаписывает, если файл не менялся локально. Иначе — конфликт, решает человек |
| `seeded` | проект (создан из шаблона один раз) | Не трогает; может предложить изменения |
| `project` | проект | Не трогает |

`AGENTS.md` смешанный: управляемый блок между маркерами `<!-- agentic:begin -->` и `<!-- agentic:end -->`,
остальное принадлежит проекту. Механизмы подключения файлов у агентов разные (`@import` есть только у Claude),
поэтому используем маркеры.

Класс и хэш каждого `managed`-файла на момент установки записываются в `agentic.lock`. Это база для
трёхстороннего сравнения при обновлении: без неё нельзя отличить изменение шаблона от локальной правки.

### 5.3. Модули и профили

Модуль — набор файлов в раскладке проекта плюс необязательные шаги установки. Профиль — список модулей
с параметрами.

| Модуль | Состав |
|---|---|
| `core` | Всегда: `AGENTS.md`, `.agents/`, `Toolbox/agentic/`, правила `Runtime/`, настройки git |
| `knowledge` | `Knowledge/`, `tb kb`, библиотекарь, skills работы со Знаниями |
| `resources` | `Resources/`, каталог, `tb resources` |
| `obsidian` | Настройка хранилища на машине |
| `devcontainer` | Опционально, см. [§10.5](#105-docker-модуль-devcontainer) |

Набор профилей v1 — открытый вопрос.

### 5.4. Хостинг и версии

- Шаблон — публичный репозиторий `agentic-project-template` на GitHub.
- URL шаблона записывается в `agentic.lock` при init (берётся из `origin` клона). Проект, развёрнутый
  из форка, обновляется из этого форка.
- Разработка идёт в основной ветке. **Релиз** — это git-тег `vX.Y.Z`. Update берёт последний релиз,
  а не текущее состояние ветки, поэтому незавершённые изменения в проекты не попадают.
- Нумерация по semver:

  | Часть | Когда увеличивается |
  |---|---|
  | major | Нужна миграция структуры проекта или формата Знаний; несовместимо меняются команды `tb` или протокол в `AGENTS.md` |
  | minor | Новые skills, адаптеры, модули, команды `tb` — без поломки существующего |
  | patch | Исправления |

- Начинаем с `v0.1.0`. Пока major равен нулю, формат ещё может меняться, но миграции всё равно обязательны.
- Релиз состоит из раздела в `CHANGELOG.md` (с подразделом «Миграции»), обновлённого `setup/VERSION`
  и тега. Перед релизом обязательно проходит проверка переводов ([§5.5](#55-языки)).

### 5.5. Языки

Шаблон поставляется на русском (по умолчанию) и английском. Язык выбирается при init и записывается
в `agentic.lock`. Проект получает **один** язык: дублирование живёт только в шаблоне и не раздувает
контекст агента.

**Что переводится** — всё, что попадает в проект или первым читает человек:

- `README.md` шаблона (английская версия — `README.en.md`);
- блок шаблона в `AGENTS.md`;
- README каталогов и шаблоны заметок;
- `SKILL.md` и промпты субагентов.

**Что не переводится:**

- `setup/DESIGN.md` — внутренний документ шаблона;
- `AGENTS.md` шаблона, `setup/INIT.md`, `setup/UPDATE.md`, `CHANGELOG.md` — их читает агент и пересказывает
  человеку на языке проекта;
- код, имена файлов и skills, ключи и значения перечислений во frontmatter;
- сообщения `tb` — всегда на английском, их читают в основном агенты.

**Раскладка.** Переводимый файл хранится в payload парой `<name>.ru.<ext>` и `<name>.en.<ext>`. Init
устанавливает нужный вариант под именем `<name>.<ext>`, например `SKILL.en.md` → `SKILL.md`. Хэш
в `agentic.lock` считается от установленного варианта.

**Источник правды — русская версия**, английская производная: агент обновляет её после каждого изменения
русской. `setup/i18n_check.py` проверяет парность: у каждого файла есть пара, совпадают структура
заголовков, блоки кода, команды и ключи frontmatter. Без прохождения проверки релиз не выпускается.

**Смена языка** в развёрнутом проекте — это переустановка `managed`-файлов на другом языке через механизм
обновления. Файлы классов `seeded` и `project` автоматически не переводятся.

**Возможное развитие:** разделить «язык инструкций для агента» и «язык документации». Слабые и китайские
модели, как правило, точнее следуют инструкциям на английском.

## 6. Жизненный цикл

### 6.1. Инициализация нового проекта

```
git clone <шаблон> my-project
cd my-project
./init.sh      # на Windows: init.cmd
```

Или открыть Агента в папке и попросить инициализировать проект: `AGENTS.md` шаблона направит его
в `setup/INIT.md`.

Шаги:

1. **Bootstrap:** найти или скачать uv ([§10.2](#102-uv-внутри-проекта)).
2. **Проверка:** это свежий клон шаблона без локальных изменений.
3. **Параметры:** имя проекта, язык, профиль, модули, агенты на этой машине, ресурсы. Собирает их агент
   по `setup/INIT.md`, либо они передаются флагами при неинтерактивном запуске.
4. **Сборка:** модули профиля копируются в корень, переводимые файлы ставятся на выбранном языке,
   подставляются параметры.
5. **Удаление инсталлятора:** `setup/`, `payload/`, `init.*`, `README.md`, `README.en.md`, `CHANGELOG.md`
   и `AGENTS.md` шаблона. `README.md` и `AGENTS.md` заменяются файлами из payload.
6. **`agentic.lock`:** URL шаблона, версия, коммит, язык, профиль, модули, хэши `managed`-файлов.
7. **Новый git:** удалить `.git` шаблона, выполнить `git init`, применить настройки git
   ([§7.4](#74-настройки-git)), сделать первый коммит `agentic: init from template vX.Y.Z`.
   Шаг деструктивный и выполняется только после подтверждения.
8. **Настройка машины** ([§6.3](#63-новая-машина)).
9. **Содержательная часть (Агент):** проектная часть `AGENTS.md`, каталог ресурсов, первые Entities.

### 6.2. Обёртывание существующих проектов (adopt)

Это инициализация плюс перенос того, что уже есть:

- Существующие репозитории **клонируются заново** в `Resources/`, а не перемещаются. Перемещение меняет
  абсолютный путь, и всё, что к нему привязано (история и память агентов, настройки IDE), отвалится.
  Старая копия остаётся, пока миграция не закончена.
- `AGENTS.md`, `CLAUDE.md` и `.claude/` внутри репозиториев остаются на месте: они принадлежат
  репозиторию и его команде.
- Личные знания собираются в `Knowledge/`: встроенная память агентов (например,
  `~/.claude/projects/<путь>/memory/`), заметки, личные инструкции. Агент раскладывает их по типам,
  человек подтверждает.

### 6.3. Новая машина

`git clone <репозиторий проекта>`, затем `Toolbox/tb setup`:

- скачать uv и Python в `Runtime/`;
- создать адаптеры выбранных агентов (`tb agents link`);
- применить настройки git и Obsidian (если модуль включён);
- предложить склонировать ресурсы из каталога.

Та же команда восстанавливает среду после удаления `Runtime/` и подключает нового агента.

### 6.4. Обновление

Запускается изнутри проекта skill-ом `agentic-update`. Skill намеренно тонкий: вся логика обновления
берётся из **свежей** версии шаблона, поэтому обновляется и сам механизм обновления.

1. **Предусловия:** корневой репозиторий чистый, незакоммиченные Знания закоммичены.
2. **Загрузка:** `tb update fetch` клонирует последний релиз шаблона (URL из `agentic.lock`, [§5.4](#54-хостинг-и-версии))
   в `Runtime/update/<версия>/`. Если новее установленного релиза нет, обновление на этом заканчивается.
3. **Инструкция:** Агент выполняет `setup/UPDATE.md` из свежей копии.
4. **План:** `update.py plan` раскладывает файлы по статусам:
   - `managed` без локальных изменений — заменить;
   - `managed` с локальными изменениями — конфликт;
   - новые и удалённые файлы;
   - миграции между версиями.
5. **Оценка:** Агент читает `CHANGELOG.md` между версиями и показывает человеку, что меняется, какие риски
   (особенно миграции Знаний и конфликты) и что нужно сделать.
6. **Подтверждение** человеком.
7. **Применение** в ветке `agentic/update-<версия>`: файлы, миграции, `tb kb lint`, `tb agents link`,
   `tb agents doctor`.
8. **Фиксация:** коммит `agentic: update to vX.Y.Z` с тезисами, обновление `agentic.lock`. Слияние — после
   подтверждения, откат — средствами git.
9. **Очистка** `Runtime/update/`.

Формат Знаний меняют только детерминированные идемпотентные скрипты из `setup/migrations/`. Переводимые
файлы обновляются на языке проекта из `agentic.lock`.

## 7. Git

### 7.1. Один корневой репозиторий

Корень проекта — git-репозиторий.

- **Отслеживаются:** `AGENTS.md`, `README.md`, `.agents/`, `Knowledge/`, `Toolbox/`, `Resources/README.md`,
  `Resources/resources.toml`, служебные файлы git.
- **Не отслеживаются:** содержимое `Resources/*` (у ресурсов свои репозитории), `Runtime/`, выходы адаптеров,
  `Knowledge/.obsidian/`, `.env*`, мусор ОС и редакторов.

Remote добавляется по желанию: личный бэкап или общий репозиторий команды.

### 7.2. Коммиты Агентом

- Только по команде или явной просьбе.
- Только явные пути; `git add -A` и `git add .` запрещены.
- Формат: `<scope>: <суть>`, в теле — ключевые тезисы изменений.
  Scopes: `knowledge`, `agents`, `toolbox`, `resources`, `agentic` (init и update).
- Перед коммитом срабатывает `pre-commit` из `.agents/git-hooks/`: `tb kb lint` и поиск секретов
  в индексируемых файлах.

### 7.3. Репозитории ресурсов

Коммиты в ресурсы делаются внутри них (`git -C Resources/<name> …`). Код ресурсов в корневой репозиторий
не попадает.

### 7.4. Настройки git

Ставит `tb setup`:

- `core.hooksPath=.agents/git-hooks`;
- `core.quotePath=false` — иначе кириллица в выводе git превращается в `\320\227…` и сбивает агентов;
- на Windows — `core.longpaths=true`.

## 8. Ресурсы

`Resources/resources.toml` — каталог всех известных ресурсов проекта, хранится в git. У конкретного человека
может быть склонирован любой поднабор.

```toml
[[resource]]
name = "api"                         # имя каталога в Resources/
kind = "git"                         # git | folder
url = "git@github.com:org/api.git"
branch = "main"
description = "Бэкенд API"
entity = "Knowledge/Entities/api.md"
```

- `tb resources status` — что склонировано, текущая ветка, есть ли изменения.
- `tb resources clone <name>` и `tb resources add <url>`.
- Если задаче нужен несклонированный ресурс, Агент предлагает его склонировать.
- Работая внутри ресурса, Агент читает его собственные `AGENTS.md`/`CLAUDE.md`, если они есть.
  Вложенные инструкции разные агенты подхватывают по-разному, поэтому это правило записано явно.
- Задача хранит, какие ресурсы и ветки она затрагивает (поле `resources`).
- **Видимость для поиска:** `Resources/*` игнорируется корневым git, а поиск агентов (ripgrep) уважает
  `.gitignore`. Лечится разрешающим правилом в `.ignore` — проверить на пилоте.

## 9. Знания

### 9.1. Правила

- Храним только то, что нельзя восстановить из Ресурсов и истории git.
- Одна заметка — одна тема. Сначала ищем существующую и обновляем её, а не плодим дубликаты.
- Относительные даты превращаем в абсолютные.
- Имена файлов — латиница, lowercase kebab-case. Заголовок и текст — на языке проекта.
- Ссылки — относительные markdown-ссылки: их одинаково понимают агенты, IDE, GitHub и Obsidian.
- Никаких секретов.
- Индекс не ведётся руками: `tb kb index` генерирует его из frontmatter.
- Пишет в Знания основной Агент; коммит — по команде.

### 9.2. Общий frontmatter

```yaml
---
type: gotcha          # decision | entity | example | gotcha | plan | task
title: Заголовок на языке проекта
description: Одна строка — по ней ищут и решают, открывать ли заметку
status: active        # допустимые значения зависят от типа
created: 2026-10-08
verified: 2026-10-08  # когда последний раз сверено с реальностью
tags: []
aliases: []           # синонимы на русском и английском для поиска
resources: []         # имена из resources.toml
---
```

Ключи и значения перечислений — латиницей. Схему проверяет `tb kb lint`.

### 9.3. Типы заметок

| Тип | Что хранит | Статусы | Срок жизни |
|---|---|---|---|
| Decisions | Архитектурные решения (ADR): контекст, решение, отвергнутые альтернативы, последствия | `proposed`, `accepted`, `superseded` (+ `superseded_by`) | Постоянно |
| Entities | Карточка сущности: назначение, где лежит в Ресурсах, связи, неочевидные инварианты, владельцы. Не пересказ кода | `active`, `deprecated` | Пока сущность жива |
| Examples | Переиспользуемые примеры и шаблоны — пассивный справочник (процедуры оформляются как skills) | `active`, `outdated` | Пока актуальны |
| Gotchas | Симптом, причина, обход, как проверить актуальность; поле `applies_to: [node@22]` | `active`, `resolved` | Пока жива причина |
| Plans | Идеи, отложенное, обнаруженное по ходу работы | `idea`, `ready`, `dropped` | До превращения в задачу или отказа |
| Tasks | Спецификация текущей задачи: цель, детали, решения по ходу, прогресс, итоги для Знаний | `active`, `blocked`, `done` | До сбора итогов |

Решения, принятые внутри задачи, живут в задаче и уходят вместе с ней. В Decisions попадают только те,
что переживают задачу.

Задача — файл `Tasks/<slug>.md`. Если нужны артефакты — папка `Tasks/<slug>/` с основной заметкой `index.md`.

### 9.4. Жизненный цикл

```
Plans (idea) ──► Tasks (active) ──► done ──► сбор итогов ──► удаление задачи
                                                 │
                             Decisions / Gotchas / Entities / Examples
```

Удалённая задача остаётся в истории git.

### 9.5. Ревью

Skill `kb-review` запускается по просьбе или по напоминанию и проверяет:

- `tb kb stale`: давно не перепроверялось или `applies_to` не совпадает с версиями в ресурсах;
- завершённые задачи без собранных итогов;
- superseded-решения, на которые всё ещё ссылаются;
- битые ссылки.

### 9.6. Obsidian

Корень хранилища — `Knowledge/`. Каталог `.obsidian/` не хранится в git. Модуль `obsidian` на каждой машине
пишет минимальную конфигурацию:

- markdown-ссылки вместо `[[wikilinks]]`;
- относительные пути;
- папка шаблонов `_templates`.

Шаблоны общие для Obsidian и `tb kb new`.

## 10. Toolbox и среда выполнения

### 10.1. Назначение

Toolbox — инструменты проекта и слой независимости от хостовой системы.
Требования к хосту: **Агент, git и доступ в интернет при первом запуске**. Всё остальное Toolbox привозит сам.

### 10.2. uv внутри проекта

- Инструменты пишутся на Python. Зависимости объявляются в самом скрипте (PEP 723), версии фиксируются
  (`requires-python`, `exclude-newer`).
- `Toolbox/tb` (POSIX sh, включая Git Bash) и `Toolbox/tb.cmd` (cmd и PowerShell) — единственное место
  с bootstrap-логикой:
  1. взять uv из PATH, если версия подходит;
  2. иначе скачать закреплённую версию в `Runtime/tools/uv/` и проверить sha256. На Windows 10+ хватает
     встроенных `curl.exe`, `tar.exe` и `certutil`; PowerShell, если понадобится, вызывается только
     с `-ExecutionPolicy Bypass`;
  3. выставить `UV_PYTHON_INSTALL_DIR=Runtime/tools/python` и `UV_CACHE_DIR=Runtime/cache/uv`;
  4. запустить инструмент через `uv run`.
- Глобально ничего не ставится, права администратора не нужны. Удаление `Runtime/` удаляет среду,
  следующий вызов `tb` восстанавливает её.
- Прокси и зеркала: стандартный `HTTPS_PROXY`, `UV_PYTHON_INSTALL_MIRROR`, переопределяемый URL загрузки uv.
- `init.sh` и `init.cmd` шаблона используют ту же bootstrap-логику.

### 10.3. Состав

- `Toolbox/agentic/` — управляемые инструменты шаблона: `kb`, `agents`, `resources`, `update`, `setup`,
  `obsidian`, `hook`.
- Остальное — инструменты проекта. Запускаются через `tb run <script>` и описываются в `Toolbox/README.md`.

### 10.4. Соглашения для вывода

- Пути — относительно корня проекта, через `/`.
- По умолчанию — компактный текст, `--json` — для машинной обработки.
- Пустой результат сообщается явно.
- При ошибке — ненулевой код возврата.
- Сообщения — на английском, независимо от языка проекта ([§5.5](#55-языки)).

### 10.5. Docker (модуль `devcontainer`)

Docker не основной способ запуска Toolbox:

- требует установки с правами администратора и виртуальную машину (Docker Desktop платный для крупных компаний);
- добавляет задержку к каждому вызову, что критично для хуков;
- на Windows не может создать адаптеры для нативных агентов;
- усложняет пути, права на файлы и git.

Зато в контейнере удобно запускать **самого Агента**: песочница для автономного режима, изоляция агентов
и моделей с меньшим доверием, полная воспроизводимость. Модуль `devcontainer` добавляет `.devcontainer/`
с CLI агентов и uv. Toolbox внутри работает так же, как на хосте.

## 11. Агенты и адаптеры

### 11.1. Уровни возможностей

| Уровень | Агент умеет | Как работает система |
|---|---|---|
| 0 | Читать `AGENTS.md` и выполнять команды | Протокол записан текстом в `AGENTS.md`. Процедуры: «найди подходящий skill в `.agents/skills/` и прочитай `SKILL.md`». Инструменты — `tb` |
| 1 | Нативные skills | Skills подхватываются автоматически |
| 2 | Субагенты | Библиотекарь и другие работают в изолированном контексте |
| 3 | Хуки | Автонапоминания, подстановка результатов `kb` |

Уровень 0 обязан работать полностью: это гарантия для новых и более слабых агентов.

### 11.2. Канонические форматы

- **Инструкции** — `AGENTS.md`.
- **Skills** — `.agents/skills/<name>/SKILL.md` по стандарту Agent Skills: имя каталога совпадает с `name`,
  kebab-case; `scripts/`, `references/`, `assets/` — по необходимости.
- **Отдельного `commands/` нет**: любая процедура оформляется как skill. В Claude Code пользовательские
  команды объединены со skills, Codex вызывает skills напрямую.
- **Субагенты** — `.agents/agents/<name>.md`, frontmatter без привязки к конкретному агенту:

  ```yaml
  ---
  name: librarian
  description: …
  model: fast        # fast | balanced | strong — адаптер переводит в конкретную модель
  tools: read-only   # read-only | edit | shell
  ---
  ```

- **Хуки** — `.agents/hooks/hooks.toml` с абстрактными событиями `session-start`, `prompt-submit`,
  `before-tool`, `after-tool`, `stop`. Команда хука всегда `Toolbox/tb hook <name>`. События, которые агент
  не поддерживает, адаптер пропускает с предупреждением.
- **MCP** — `.agents/mcp.toml`.

### 11.3. Манифест адаптера

`.agents/adapters/<agent>/adapter.toml` описывает, как агент видит систему. Пример (схема уточняется
при реализации):

```toml
name = "claude"
tier = 3
instructions = "native"          # читает AGENTS.md сам; иначе — сгенерировать заглушку

[skills]
mode = "link"                    # native | link | none
target = ".claude/skills"

[subagents]
target = ".claude/agents"
models = { fast = "haiku", balanced = "sonnet", strong = "opus" }

[hooks]
target = ".claude/settings.json"
events = { session-start = "SessionStart", prompt-submit = "UserPromptSubmit", before-tool = "PreToolUse", after-tool = "PostToolUse", stop = "Stop" }

[mcp]
target = ".mcp.json"

[memory]
disable = true                   # отключить встроенную память агента

outputs = [".claude/", ".mcp.json"]   # попадают в .gitignore
```

Генераторы форматов лежат в `Toolbox/agentic/adapters/`.

### 11.4. Команды

- `tb agents link [<agent>…]` — создать ссылки и сгенерировать конфиги на этой машине (идемпотентно).
- `tb agents doctor` — проверить, что всё на месте и актуально.
- `tb agents list` — доступные адаптеры и их уровни.

Ссылки на каталоги — symlink, а на Windows без прав — junction. Ссылки на файлы не используются.

### 11.5. Расширение

Новый агент — это новый каталог в `.agents/adapters/` и, при необходимости, генератор. Ядро не меняется,
новые адаптеры приходят в проекты обычным обновлением.

Китайская или опенсорсная **модель** внутри уже поддержанного агента (через совместимый API) адаптера
не требует. Для неё важны надёжность уровня 0 и инструмент `kb`.

### 11.6. Стартовые адаптеры

- **claude** — уровень 3. `AGENTS.md` читает сам (если нет `CLAUDE.md`). Skills видит через ссылку
  `.claude/skills`. Субагенты, хуки и MCP генерируются, встроенная авто-память отключается.
- **codex** — `AGENTS.md` и `.agents/skills` читает нативно. Поддержку субагентов, хуков, проектного
  конфига и MCP уточняем при реализации.

## 12. Контекст и библиотекарь

### 12.1. Бюджет старта

При старте сессии в контекст попадают `AGENTS.md` целиком и описания всех skills и субагентов (плюс MCP,
если подключён). Поэтому:

- `AGENTS.md` — не больше ~1500 токенов: карта, правила, ссылки. Размер проверяет `tb kb lint`;
- skills — немного и с точными описаниями;
- Знания при старте не читаются.

Скелет `AGENTS.md`:

1. О проекте — 2–3 строки (проектная часть).
2. Карта каталогов (управляемый блок).
3. Правила (управляемый блок):
   - память — только `Knowledge/`, встроенную память агента не использовать;
   - временные файлы — в `Runtime/`;
   - коммиты — только по команде;
   - `Resources/*` — отдельные репозитории со своими инструкциями;
   - где лежат skills и как ими пользоваться без нативной поддержки;
   - команды `tb` (на Windows `Toolbox\tb.cmd`).
4. Протокол сессии (управляемый блок).
5. Особенности проекта (проектная часть).

### 12.2. Библиотекарь

Логика живёт в skill `kb-lookup`, так что она переносима. Субагент `librarian` — обёртка для изолированного
контекста. Где субагентов нет, skill выполняется в основной сессии, в крайнем случае хватает `tb kb search`.

**Когда обращаться:**

- перед планированием задачи;
- перед принятием решения;
- при первом касании сущности в сессии;
- когда ошибка кажется знакомой.

**Процесс:** `tb kb search` → чтение лучших совпадений → сверка утверждений с Ресурсами (версии в lock-файлах
зависимостей, существование файлов и функций) → ответ.

**Формат ответа:**

```
Ответ: …
Источники: Knowledge/Gotchas/….md, …
Проверка: confirmed | stale? | unverifiable (почему)
Предложения по Знаниям: … (если что-то устарело)
```

Если ничего не найдено, это сообщается явно.

Библиотекарь только читает, правки Знаний вносит основной Агент. Пути в ответе обязательны: если пересказ
потерял нюанс, основной Агент откроет оригинал.

### 12.3. Поиск: `tb kb`

| Команда | Назначение |
|---|---|
| `search <запрос>` | BM25 и стемминг Snowball (RU/EN) по `title`, `description`, `aliases`, `tags` и тексту; фильтры `--type`, `--status`, `--resource` |
| `show <путь>` | Заметка целиком |
| `related <путь>` | Ссылки и обратные ссылки |
| `new <type> <slug>` | Новая заметка из шаблона |
| `index` | Индекс из frontmatter |
| `lint` | Схема frontmatter, ссылки, имена файлов, секреты, бюджет `AGENTS.md` |
| `stale` | Кандидаты на перепроверку |

- Индекс строится в памяти: Знаний немного. Кэш в `Runtime/cache/` — если понадобится.
- Интерфейс — CLI, а не MCP: описания MCP-инструментов занимают контекст при старте. MCP-обёртка
  и семантический поиск — позже и опционально.
- Для агентов с хуками: на `prompt-submit` выполняется `tb kb search --brief` по тексту запроса, и в контекст
  попадают только заголовки и пути найденных заметок.

## 13. Протокол сессии и базовые skills

**Протокол:**

- **Старт:** `AGENTS.md`; при необходимости — список активных задач (`tb kb search --type task --status active`,
  только заголовки).
- **Работа:** перед решениями — `kb-lookup`; временные файлы — в `Runtime/`.
- **Завершение:** `wrap-up`.
- **Периодически:** `kb-review`.

**Базовые skills:**

| Skill | Назначение |
|---|---|
| `kb-lookup` | Библиотекарь: найти и проверить ответ в Знаниях |
| `wrap-up` | Итоги сессии: статус задач, отложенное в Plans, найденные грабли в Gotchas, предложения ADR; предложить коммит |
| `kb-commit` | `tb kb lint` и коммит Знаний с ключевыми тезисами |
| `kb-review` | Ревью Знаний ([§9.5](#95-ревью)) |
| `agentic-update` | Обновление проекта из шаблона ([§6.4](#64-обновление)) |

Инициализация — это не skill: до неё адаптеры ещё не созданы. Её ведёт инструкция `setup/INIT.md`.

## 14. Кроссплатформенность

Чек-лист:

- Симлинки не коммитятся. Каталоги связываются через symlink или junction, файловых ссылок нет.
- Входы: `.sh` и `.cmd`. PowerShell — только с `-ExecutionPolicy Bypass`.
- `.gitattributes`: `* text=auto eol=lf`, для `*.cmd` и `*.bat` — `eol=crlf`.
- Имена файлов — латиница, kebab-case, без запрещённых в Windows символов и имён (`CON`, `NUL`, …).
  Проверяет `tb kb lint`.
- Настройки git — [§7.4](#74-настройки-git).
- Пути в выводе инструментов — относительные, через `/`.
- Регистр имён каталогов фиксирован.
- Проверка на macOS и Windows — обязательная часть пилота.

## 15. Безопасность

- Секреты не попадают в `Knowledge/`, `Toolbox/` и `.agents/`. `.env*` — в `.gitignore`, поиск секретов —
  в pre-commit.
- uv скачивается закреплённой версии с проверкой sha256.
- Источник обновлений — только URL из `agentic.lock`. Сменить источник может только человек.
- В `Runtime/` могут оказаться логи с чувствительными данными: он не в git и очищается осознанно.
- Агентов и модели с меньшим доверием запускаем в `devcontainer`.

## 16. Открытые вопросы

1. **Профили v1.** Предложение: `software` (ресурсы — git-репозитории с кодом) и `generic` (минимальный набор
   для проектов без кода: документация, исследования). Нужен список типов проектов, которые предвидятся.
2. **ripgrep и `Resources/*`.** Работает ли разрешающее правило в `.ignore` для поиска Claude (Grep/Glob)
   и Codex.
3. **Worktree и параллельные сессии.** Worktree корневого репозитория не содержит ресурсов, а Claude desktop
   создаёт такие worktree для сессий. Варианты:
   - worktree внутри ресурсов;
   - ссылки на ресурсы при создании worktree;
   - отказ от worktree-режима на уровне корня.
4. **Codex.** Уточнить текущую поддержку субагентов, хуков, проектного конфига, MCP и встроенной памяти.
5. **Claude Code.** Точный ключ отключения авто-памяти. Как обнаруживаются skills через ссылку на каталог
   (запасной вариант — ссылка на каждый skill).
6. **Пороги устаревания** по типам заметок для `tb kb stale`.
7. **Хуки v1.** Кандидаты: `prompt-submit` → подстановка результатов `kb`, `stop` → напоминание о `wrap-up`.

- Claude Code читает `AGENTS.md`, если в каталоге нет `CLAUDE.md` (с версии 2.1.277, сентябрь 2026).
