# Decisions — решения

Архитектурные решения (ADR): почему сделано так, а не иначе. Код показывает, что сделано; решение
хранит контекст, отвергнутые альтернативы и последствия. Тип `decision`, срок жизни — постоянно.

## Когда создавать

- Решение затрагивает несколько ресурсов, задач или людей и переживёт текущую задачу.
- Были реальные альтернативы, и к выбору наверняка вернутся с вопросом «почему так?».

## Когда не создавать

- Решение действует только внутри задачи — запиши в «Решения по ходу» задачи.
- Выбор очевиден из кода или описан в документации ресурса.
- Это пока идея — в Plans.

## Статусы

- `proposed` — предложено, ждёт решения человека. Агент создаёт решения только в этом статусе.
- `accepted` — принято; переводит человек или Агент с его явного согласия.
- `superseded` — заменено другим; обязательно `superseded_by: Decisions/<slug>.md` и ссылка на новое решение в тексте.
- Отклонённое предложение удали; если причина отказа важна — запиши её в «Альтернативы» принятого решения.

## Имя и создание

Имя файла — суть решения: `use-uv-for-tools.md`, `single-root-repo.md`.

`Toolbox/tb kb new decision use-uv-for-tools --title "Инструменты запускаем через uv"`

## Пример (фрагмент)

```markdown
title: "Инструменты запускаем через uv"
description: "Toolbox не требует Python на машине: uv ставит его в Runtime/"
## Решение
Скрипты Toolbox — Python с PEP 723, запуск через `Toolbox/tb run`.
## Альтернативы
Системный Python — разные версии на машинах; Docker — тяжело и медленно для хуков.
```
