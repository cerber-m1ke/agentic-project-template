# Ревью Знаний

## Цель и результат

В Знаниях остаётся только живое, верное и неочевидное. Ревью закончено, когда:

- у каждой заметки в охвате есть вердикт с доказательством;
- подтверждённые человеком действия применены, `Toolbox/tb kb lint` без ошибок;
- человек получил отчёт и вопросы.

## Границы

- Охват по умолчанию — Decisions, Entities, Gotchas, Examples, Tasks. Человек может сузить его: тип,
  ресурс, список путей, только `tb kb stale`. Plans — skill `plan-review`.
- Меняешь только `Knowledge/`. Ошибки в Ресурсах, коде, `.agents/` не правь — вынеси в отчёт.
- Сверка — только чтение. Можно читать файлы, искать, смотреть `git log`/`show`/`branch` и версии.
  Нельзя запускать сборку, установку, тесты, `checkout`/`pull`/`fetch`. Если проверка требует
  побочных эффектов, ставь `ask`.
- Удаление, объединение, смену статуса и правку принятого решения выполняй только после подтверждения
  человека. Человек может подтвердить весь список сразу или по пунктам.
- Не коммить: в конце предложи skill `kb-commit`.

## Вердикты

Каждой заметке — ровно один вердикт:

| Вердикт | Когда | Действие |
|---|---|---|
| `keep` | Ключевые утверждения подтверждены | `verified` = сегодня |
| `fix` | Тема жива, но факты неверны (пути, версии, команды, связи) | Исправить на месте, `verified` = сегодня |
| `shrink` | Пересказывает код, README ресурса, историю git | Оставить ссылку на источник и неочевидное |
| `merge` | Пересекается с другой заметкой | Объединить в одну, перевести ссылки |
| `delete` | Отжила (см. критерии), упразднённый статус, задача `done` после сбора итогов | Перенести важное в живую заметку, удалить, убрать ссылки |
| `ask` | Проверить нельзя или нужен выбор человека | Конкретный вопрос в отчёте |

## Доказательства

Вердикт без доказательства недопустим. Доказательство — то, что человек может проверить сам:

- файл, функция, ключ найдены или не найдены: `Resources/<name>/<путь>:<строка>` или команда поиска
  с пустым результатом;
- версия из lock-файла или манифеста против `applies_to`;
- коммит: `git -C Resources/<name> log --oneline -S '<строка>'`, `git log --oneline -- <путь>` —
  когда исправили, удалили, слили ветку;
- результат проверки из раздела «Как проверить актуальность» (без побочных эффектов);
- путь другой заметки — для `merge` и для `delete` при замене.

«Похоже», «скорее всего», «давно не обновлялось» доказательствами не считаются: в таких случаях вердикт —
`ask`. Если ресурс не склонирован, тоже `ask`, а не `delete`.

## Критерии по типам

- **Gotcha.** Жива ли причина. Сверь версии `applies_to` с lock-файлами, выполни «Как проверить
  актуальность», поищи в коде исправление или обход. Причина устранена во всех используемых версиях —
  `delete`; только в части — `fix` с более узким `applies_to`.
- **Example.** Соответствует ли принятому подходу. Найди в Ресурсах 1–2 свежих места с тем же паттерном.
  Расходится — `fix` или `delete`. В коде появился канонический образец — `shrink` до ссылки или `delete`.
- **Decision.** Действует ли решение: код и конфиги соответствуют разделу «Решение». Не соответствуют —
  `ask` (решение нарушено или отменено?). Заменено другим — `delete` с переносом причины в новое.
  Если суть видна из кода и документации и вопрос «почему так?» уже не возникнет — `delete`; для `accepted`
  при сомнении — `ask`. `proposed` старше 30 дней — `ask`: принять или удалить.
- **Entity.** Существует ли сущность. Проверь пути, точки входа, связи и владельцев. Пересказ кода —
  `shrink`. Сущность `deprecated`, которой уже нет, — `delete`.
- **Task.** `done` — разнеси «Итоги для Знаний» по правилам skill `wrap-up`, затем `delete`.
  `active`/`blocked` без обновлений 30 дней — `ask`. Сверь прогресс с коммитами и проверь ветки:
  `git -C Resources/<name> branch -a --list '<ветка>'`, `git -C Resources/<name> branch --merged`.
- **Все типы.** `description` отражает суть, ссылки не битые и не ведут на удаляемое, нет дубликатов,
  нет секретов.

## Порядок

1. **Сбор.** `Toolbox/tb kb lint`, `Toolbox/tb kb stale`, `Toolbox/tb kb index --json`,
   `Toolbox/tb resources status` (Windows PowerShell: `Toolbox\tb.cmd …`). Составь список заметок в охвате.
2. **Пачки.** Разбей заметки на пачки по 5–8, по возможности по одному ресурсу на пачку: так субагент
   читает один ресурс. Заметки без ресурса — отдельной пачкой.
3. **Проверка.** Если агент умеет запускать субагентов и доступен `kb-auditor`, запусти его на каждую
   пачку параллельно, все вызовы одним сообщением. Передай пути заметок, сегодняшнюю дату и охват.
   Если субагентов нет или заметок меньше шести, проверь сам по тем же критериям и в формате `kb-auditor`.
4. **Сведение.** Собери вердикты и сам проверь то, что не видно внутри пачки: пересечения между пачками,
   ссылки на заметки с `delete` и `merge`. Вердикт со слабым доказательством перепроверь или переведи в `ask`.
5. **Отчёт.** Покажи человеку отчёт в формате ниже. Для `delete` и `merge` укажи, что и куда
   переносится. Дождись подтверждения.
6. **Применение** — только подтверждённого, по порядку: перенос важного → `merge` → `fix`/`shrink` →
   `delete` → правка ссылок → `verified`.
7. **Проверка.** `Toolbox/tb kb lint` — ни ошибок, ни предупреждений об упразднённых статусах.
   `Toolbox/tb kb stale` — в охвате остались только заметки с вердиктом `ask`.
8. **Итог.** Числа по вердиктам, применённое, открытые вопросы. Предложи skill `kb-commit`.

## Формат отчёта

```
Ревью Знаний <ГГГГ-ММ-ДД> — охват: <…>; проверено: N
keep: N · fix: N · shrink: N · merge: N · delete: N · ask: N

| Заметка | Вердикт | Доказательство | Действие |
|---|---|---|---|
| Knowledge/Gotchas/uv-proxy-ssl.md | delete | Resources/api/uv.lock: uv 0.14 (applies_to uv@0.12); исправлено в 0.13 — Resources/api/CHANGELOG.md:12 | удалить; ссылка из Entities/api.md |

Вопросы к человеку:
1. Knowledge/Decisions/<slug>.md — <вопрос>
```

Строки с `keep` можно свернуть в одну: `keep: <пути>`.
